# 能力契约规范

> 状态：能力设计与演进规范。本文的目标字段不代表当前注册表已经实现或运行时已经执行。
> 本项目现有唯一宿主能力登记源为 `src/services/pluginProtocolRegistry.json`；执行治理边界见 [统一调度规范](统一调度规范.md)。

## 1. 核心原则

**能力是稳定的外部语义，handler 是可替换的内部实现。**插件只依赖能力 ID、schema、权限/开放状态、失败与副作用语义；不依赖 `services/*` 类名、文件布局、存储格式、HTTP 路径、队列名或内部事件。

能力 ID 表示一个版本化的业务动作，不表示代码位置。举例：`message.send@1` 表示按该版本契约提交一条宿主消息发送请求；它不承诺某个 Python 函数名或具体微信发送通道。

## 2. 能力条目内容

当前 `registry.calls` 条目已有 `inputSchema`、`outputSchema`、`sideEffect`、`needsApproval`、`enabled` 等信息；插件清单白名单由 `levels.4.calls` 控制。`invokeHost` 已提供每能力独立的有限并发/等待准入及等待取消、超时和执行前授权复核；上限由 dispatcher 构造参数设置，不是注册表执行策略字段。同一 dispatcher 的活动嵌套 `invokeHost` 还会继承父调用的 deadline（取较小值，不扩张）与取消来源（多来源合成派生 signal），详见 [统一调度规范](统一调度规范.md) 第 2.1 节；这也不改变注册表字段。当前没有逐能力资源域/优先级/硬取消的统一登记字段，不能把下表建议字段误认为已经实现。

新能力规范审查至少应记录以下信息（优先补充仓库现有能力注册表模型；不在未完成运行时支持前虚构字段并宣称有效）：

| 信息 | 要回答的问题 | 兼容性要求 |
| --- | --- | --- |
| `id` | 稳定业务动作是什么？格式为 `domain.verb@major` | 发布后不复用 ID；版本只表达契约不兼容变更 |
| `inputSchema` | 调用方能传什么？哪些字段必需、大小/范围如何限制？ | 必须可在边界校验；不得依赖隐式默认猜测关键语义 |
| `outputSchema` | 成功、排队、处理中或外部确认如何表达？ | 保持字段类型和既有含义；不以宽泛 JSON 掩盖契约 |
| `visibility` / allowlist | 宿主内部、哪些插件等级或哪些调用方可见？ | 默认不向插件开放；开放需要权限与数据最小化审查 |
| `authorization` | 是否需要用户批准，授权粒度和调用者是谁？ | 每次调用按现有授权代次规则复核；不因内部调用免除传输鉴权 |
| `sideEffect` | 无副作用、网络读取、本地写、计费、外部动作中的哪种？ | 决定回退、重试、幂等和故障传播规则 |
| `executionClass`（目标） | inline、request、chat-serial、background、external-effect 或 isolated？ | 只有执行器实际支持后登记才具有效力；否则文档和测试不得声称生效 |
| `timeoutBudget`（目标） | 排队与执行的总预算是多少，是否继承上游 deadline？ | 用总 deadline；不得在下游重置完整预算。当前仅在活动嵌套 `invokeHost` 上自动继承，不是全链路保证 |
| `cancellation`（目标） | 是否合作式取消、取消传递到哪里、不支持取消时怎样隔离？ | 取消能力必须由实现和测试证明，不能从 Promise 结束推断底层已停止。继承只传递 signal，不新增硬中断 |
| `idempotency`（目标） | 是否需要调用方幂等键、键的作用域和保留期？ | 外部副作用或不确定重试必须显式回答；未知结果不得盲目重试 |
| `resultLifecycle`（目标） | accepted、queued、claimed、completed、acknowledged 等状态及其证据是什么？ | 区分接受、提交与外部送达；不得偷换已有返回语义 |
| `observability` | 哪些安全元数据用于追踪与排障？ | 不记录正文、密钥、记忆原文或不必要的稳定个人标识 |

目标字段名称仅用于讨论数据模型，不是要求当前立即逐字加入 JSON。字段应由一份机器可校验定义承载，并通过统一 schema/验证器检查；避免注册表、启动器、作者 CLI 与文档各维护一套事实源。

## 3. 版本策略

- **不改变契约**：内部重构、拆分 handler、改存储、换供应商或执行器；输入输出、权限、可观察时机、错误/副作用语义均不变时保持原 ID 和主版本。
- **兼容扩展**：可选输入字段、可选输出字段等只有在所有旧调用方仍按原语义工作的前提下才可原地扩展。需要核对 schema 校验是否允许额外字段，以及插件是否可能严格比对完整输出；不能仅凭“字段是可选的”就认定兼容。
- **不兼容变化**：必填字段/类型改变、含义改变、权限扩大、原有成功变成 queued、确认等级改变、错误后果或幂等语义改变，创建新主版本 ID（如 `message.send@2`），不得在 `@1` 下静默改变。
- **并行迁移**：新旧版本可短期共存，由宿主适配层将两种契约映射到同一内部用例；旧版本迁移需记录替代能力、停用窗口和诊断结果。
- **退役**：先停止新插件采用旧能力、提供替代方案和版本窗口；在不兼容移除前检查已安装声明、授权快照及调用日志。不得复用已退役能力名表示不同动作。
- `enabled: false` 表示已登记但不能调用，不等于删除契约；保留能力尤其不可被相近新功能借用其 ID。

## 4. 插件稳定性与边界

插件 API 面由注册表中已启用、等级允许、清单声明且授权批准的能力交集决定。任一条件缺失都应拒绝调用。宿主内部能力即使使用同一个 `invokeHost`，也不会因此自动成为插件 API。

插件作者应按公开能力错误和输出语义处理。内部实现错误通常经 worker/host.call 映射为通用宿主失败；插件不应按内部错误码分支，不应在未知外部副作用结果后盲目重试。不同 provider hook 的 gate / observe / enhance / replace 语义与宿主 `calls` 能力是两类契约，不能混用所有权与回退规则。

已有能力的变更要特别保留：

- `message.send@1` 的 `queued`、`submitted` 或 `confirmed:false` 不代表微信已送达。
- `chat.handle@1` 等接管型能力的失败回退取决于是否已产生副作用；不能一律回退默认实现。
- gate/observe/enhance 是否 fail-open 或回退，遵从既有插件协议，不被通用调度包装器悄悄覆盖。
- 已发布的路径、payload、权限与错误可见面属于公开契约；内部 dispatcher/IPC 可演进，但不得造成外部行为的静默变化。

## 5. 新能力接入流程

1. **先判断是否需要新 ID**：若已有能力语义一致，复用它；不要因模块移动或重命名创建重复能力。
2. **定义业务语义**：写明调用方、目标用户/资源、成功点和明确不保证的事（如提交不等于送达）。
3. **定义输入输出**：给出严格 schema、尺寸/枚举/边界及有无状态查询；禁止把任意对象作为长期公开契约，除非确实有受限且版本化的 schema。
4. **审查安全与副作用**：确定可见等级、用户批准、数据访问、外部副作用、计费、重试与幂等策略；默认内部且最小权限。
5. **定义执行治理**：根据 [统一调度规范](统一调度规范.md) 确定 inline 或受治理任务类别、队列满结果、总 deadline、取消传递、不可取消时的隔离、关闭语义。若运行时还不支持所需策略，先实现并测试执行器支持，不能只写元数据。
6. **登记唯一契约**：更新 `src/services/pluginProtocolRegistry.json`；只有明确批准插件开放时才更新对应等级白名单。保持输入/输出 schema、权限和版本同步，不复制第二套运行时定义。
7. **实现 handler**：在 `src/services/features/<domain>.js` 对应用例模块实现；`src/services/features/index.js` 是功能 handler 唯一装配点。handler 只依赖 runtime 注入和显式依赖，不让 HTTP 路由或插件代码直连业务服务。
8. **接入调用方**：HTTP/桥接/定时任务/插件宿主调用统一走 `runtime.capabilities.invokeHost`；传输层保留身份校验、令牌、请求解析和响应适配。同步内部逻辑按调度规范的白名单保留直连。
9. **更新公开文档与生成面**：同步插件协议能力表、作者 SDK 文档、启动器目录/CLI 的生成或校验逻辑；优先由注册表生成展示，避免复制手工清单。
10. **行为测试**：至少验证 schema 拒绝、权限拒绝、路由/桥接入口实际接线、实现可替换、队列/超时/取消或明确的同步语义、副作用重复/未知结果处理、旧插件包兼容。插件可见失败与内部诊断分开断言。
11. **分阶段发布**：不兼容能力先双版本并存，记录迁移和回滚方式；未获得明确的兼容证据，不移除旧契约。

## 6. 重构能力实现的检查单

重构已有能力时，不需要插件适配，只要下面各项全部保持：

- [ ] 能力 ID 和版本不变。
- [ ] 输入/输出 schema 与默认值语义不变。
- [ ] 授权要求、插件等级白名单和数据访问范围不扩大。
- [ ] 完成时机与返回状态含义不变（特别是 queued、submitted、acknowledged）。
- [ ] 错误类别及调用方可见回退语义不变。
- [ ] 重试、幂等、副作用及未知结果语义不变。
- [ ] deadline、取消或资源治理变化没有违反公开保证；提高限制不能导致已合法调用静默失效。新增的嵌套 deadline 收缩或 signal 合并若可能让既有合法调用更早失败，要单独核对并补测试。
- [ ] 路由、桥接、插件仍经统一能力入口；没有引入平行直调路径。
- [ ] 现有插件兼容测试通过；至少一个替换 handler 的测试证明插件与内部实现解耦。

任何一项不成立，就不是单纯内部重构：需先设计新版本/迁移，并清楚记录对调用方的影响。

## 7. 规范与实现差距维护

能力契约和执行治理都属于运行时接口，规范写了不等于代码已实现。每次新增目标字段、错误码或调度保证时，必须标明：

1. 定义所在的唯一机器可读事实源；
2. 哪个运行时校验/执行组件消费它；
3. 插件、宿主内部或二者哪一侧可见；
4. 至少一个可失败的行为测试；
5. 兼容旧注册表、旧插件及旧队列任务的策略。

在执行器支持落地前，声明能力时只能使用当前代码真正识别的字段；目标策略作为设计记录，不要写入会被误认为有效的 registry 字段。详细现状与目标边界见 [统一调度规范](统一调度规范.md) 和 [插件协议](插件协议.md)。
