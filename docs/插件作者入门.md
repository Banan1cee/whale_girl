# 鲸鲸插件作者入门

鲸鲸 4.3.0 起只有一种可执行插件协议：**whale-plugin/1**，完整说明见 [插件协议](插件协议.md)。
旧的 Api 1/2/3/4 可执行插件不再运行；人设包（纯数据）继续支持。新清单用 `level` 声明权限：1 级整数、2 级文本、3 级受限回复扩展使用 `plugin.wasm`；4 级使用 `plugin.js`，并须确认完整系统权限。以下 JavaScript 模板是 4 级；Wasm 的入口与输入输出约定见协议。

## 先判断能不能做成插件

能直接用现有扩展点做的：

- 用户点一下、给个 JSON 输入、拿回 JSON 结果（`tool.run@1`）。
- 在本轮回复草稿上加内容或改口吻（`chat.reply@1` 的 `enhance`）。
- 整轮聊天交给自己的实现（`chat.handle@1` 的 `replace`，进阶）。
- 替换本轮模型生成（`chat.generate@1`）。
- 按宿主时钟周期跑任务（`task.tick@1`）。

需要宿主尚未提供的接口时，停在草稿：说明缺的能力、需要的输入输出和受影响功能，
不要靠改鲸鲸源码或让插件绕过 `host.call` 补齐。

## 四步做出第一个插件

```text
npm run plugin -- init my-tool --template tool
npm run plugin -- validate my-tool
npm run plugin -- pack my-tool --out dist/my-tool.zip
npm run plugin -- trial dist/my-tool.zip
```

1. `init` 生成 `plugin.json`、`plugin.js` 和 README。模板有 `tool`、`reply-enhancer`、
   `chat-takeover`、`scheduled-task`。
2. 改 `provides` 与 `exports.providers`，两者键必须一致；要调宿主能力就写进 `calls`。
3. `validate` / `test` 只做静态检查（清单、作用域、ZIP 结构、CommonJS 语法），**不执行插件代码**。
4. 把 ZIP 拖进启动器「插件市场 → 从本地安装」，启用时确认完整系统权限，然后在插件卡片里运行。

## 入口写法

```js
exports.providers = {
  'tool.run@1': async (input, { host, settings, signal }) => {
    const status = await host.call('status.read@1', {});
    return { chars: [...String(input.text || '')].length, appVersion: status.version };
  },
};
```

- `exports.providers[能力ID]` 是唯一入口；不要用 `hooks` / `run` / `onHook` 这些旧别名。
- `host.call(能力ID, 输入)` 只能调用清单 `calls` 里声明、且宿主已启用的能力。
- 不要读模型密钥、微信凭据或任意本地文件来绕过宿主；那属于插件自己的完整系统权限，
  用户启用前已被告知，但出了问题由作者负责。

## 清单要点

- 必填：`format`、`id`、`name`、`author`、`version`、`minAppVersion`、`description`、
  `entry`、`runtime`、`provides`、`calls`。
- `format` 固定 `whale-plugin/1`，`runtime` 固定 `node-full`，`entry` 固定 `plugin.js`。
- `id` 小写字母开头，只用小写字母、数字和短横线。
- `provides` 每项写 `mode` 和 `scope`，值必须在该能力允许范围内。
- 未知字段会被拒绝；同一个能力不能重复声明。

## 权限与安全

- 1–3 级使用受限 Wasm，3 级回复扩展须确认聊天访问。4 级 Node 以当前用户权限运行，**不是沙箱**；启用时必须确认完整系统权限。
- 安装、保存设置都不等于授权；启用才签发授权，更新或改设置后要重新确认。
- 能用 `host.call` 做的事不要自己实现（例如联网检索、调模型），这样用户能看见数据边界。
- 插件 ZIP 只放 `plugin.json` 和所需入口（1–3 级为 `plugin.wasm`，4 级为 `plugin.js`）；不要把真实会话、配置、密钥打进包。

## 自测清单

1. 正常输入、空输入、超长输入各试一次。
2. 停用后确认不再运行；重新启用后状态是否保留。
3. 改设置后确认旧结果被丢弃、新设置生效。
4. 触发一次超时或抛错，确认宿主回到默认行为而不是重复副作用。

## 审核与市场维护

- **审核怎么做**：维护者先核对清单、下载包的校验值和源码，再从市场待上架的**同一份 ZIP** 试装；可以提前审核，不必等目录合并后才开始。
- **未发布客户端可以先合并入库**：客户端正式发布前也允许先合并（这条从 4.1 起沿用）。确认目录 CI 已通过、代码可审核就合，并在 PR 里写明「所需客户端版本」；等正式客户端发布后，补一条用同一份 ZIP 的试装记录即可。
- **已发布过的能力要更严**：仍须在对应的正式客户端上试装通过再合并。
- **绑定讨论区**：市场维护者可在市场仓库的 `discussion-issues.json` 为插件绑定一个 GitHub Issue，目录生成器会写入 `DiscussionIssue`。
- **用户反馈与收藏**：用户既能在 GitHub 评论，也能在启动器内直接收藏；收藏由市场服务统一统计。
- **出问题**：可以下架对应版本；作者修好后用新版本重新投稿。
