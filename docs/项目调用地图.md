# 项目调用地图

> 目的：从入口一路追到「消息怎么进来、提示词怎么拼、模型怎么调、回复怎么发出去」。
> 基线：`feat/4.3`；调度相关链路于 2026-11-26 按工作区源码复核（含第二阶段嵌套继承与 `search.query@1` 预算接线、第三阶段准入统计与完成语义分级、第四阶段全局额度/优先级/幂等/关闭/隔离执行/持久任务与网关轮次 signal），其余章节仍保留原有说明，不能视作全量复核。
> 本文记录运行时调用；调度边界与后续目标见 [统一调度规范](统一调度规范.md)，能力演进与接入流程见 [能力契约规范](能力契约规范.md)。

## 0. 一句话总览

启动器拉起 **Node 内核** 和 **Python 桥接**；桥接把微信消息 `POST /webhook/wechat` 给内核；内核的 `Bot` 决策、拼提示词、调模型、写记忆；回复通过 HTTP 返回桥接，桥接再用微信 UI 自动化把消息发出去。

```text
WhaleLauncher.exe
  ├─ node server.js --no-browser        （内核，127.0.0.1:端口）
  └─ python examples/wechatauto_bridge.py（桥接，读写微信窗口）

微信 ←→ 桥接 ←→ /webhook/wechat ←→ Bot ←→ LLM / Store / 插件
```

## 1. 进程与入口

| 进程 | 入口 | 谁拉起 | 负责 |
| --- | --- | --- | --- |
| 启动器 `WhaleLauncher.exe` | `launcher/App.xaml.cs` → `MainWindow` | 用户双击 | 配置界面、状态页、更新、拉起/守护内核与桥接 |
| Node 内核 | `server.js` 的 `startServer()` | `launcher/RuntimeSupervisor.cs` 的 `StartNode()` | HTTP API、聊天决策、提示词、模型、记忆、定时任务 |
| Python 桥接 | `examples/wechatauto_bridge.py` → `bridge/engine.py:main()` → `bridge/app.py:BridgeRuntime.start()` | `RuntimeSupervisor.StartBridge()` | 读微信消息、调内核、用 UIA/后台通道发微信 |
| 外部网关（可选） | `POST /webhook/wechat` | 自建中转服务 | 不走本机桥接时，自己实现收发 |

启动顺序：

1. `RuntimeSupervisor.StartAllAsync()` 先 `StartNode()`。
2. 轮询 `GET /healthz`，确认 `service=whale-girl` 且 PID 对得上（`WaitForNodeAsync`）。
3. 再 `StartBridge()`，桥接启动后读 `data/bridge-ready.json` 并开始监听微信。

手工启动：`node server.js`；环境自检：`node server.js --doctor`。

## 2. 内核装配：只在一个地方注入依赖

入口是 `src/app.js` 的 `createRuntime()`。它按顺序创建：

1. `loadConfig()`：读 `config.json`，补默认值。
2. `personaStore.apply/load`：把 `data/persona.json` 合并进配置。
3. `Store`：记忆库（`data/store.json` 及其分片）。
4. `DeepSeekClient`：所有模型调用的唯一客户端。
5. `Bot`：聊天主管线（`src/pipeline/bot.js`）。
6. 各服务：`DiaryService`、`DigestService`、`StickerService`、`MomentsService`、`ReminderService`、`ContactsCache`。
7. `runtime.capabilities`：登记宿主能力 handler；聊天会话串行由 `Bot.queueSession()` 维持，接管 provider 通过同一会话队列执行。数据目录可用时还挂载 `data/host-tasks.jsonl` 持久任务表，并在启动后的下一轮事件循环异步重放一次。
8. `createGateways()`：HTTP 网关适配器。
9. `PluginHost`：给 JavaScript 插件提供宿主 API。

之后 `server.js` 只做三件事：建 HTTP server、挂 `createRouter(runtime)`、监听端口。**业务模块不要自己 `require` 单例，都从 `runtime` 拿依赖。**

P0 后，Bot 中拆出的职责模块：

| 职责 | 文件 | 说明 |
| --- | --- | --- |
| 管理命令/授权 | `src/pipeline/admin.js` | `Bot` 保留薄代理；魔咒授权、管理命令解析放在这里 |
| 表情包决策 | `src/pipeline/stickers.js` | `Bot` 保留薄代理；严肃窗口、发送催促、挑选发送计划 |
| 提示词/预算决策 | `src/pipeline/decisionPrompt.js` | 组合群风格、静态 system、tail、记忆 turns，并做输入硬预算回退 |
| 回复收尾 | `src/pipeline/finalize.js` | `Bot` 保留薄代理；清标记、清洗、写回复记忆、截断与拆气泡 |
| 用量统计 | `src/pipeline/usage.js` | `Bot` 保留薄代理；usage 累加、估算校准、成本与日志 |

`src/pipeline/bot.js` 负责把消息路由到明确阶段：`prepareIncoming()` 规范化输入，`loadMemoryContext()` 读取记忆，`computeTrigger()` 判断是否接话，`decisionPrompt.js` 拼提示词/turns 并检查预算；之后由生成和回复收尾模块继续处理。

P1 命名整理：Bot 实现位于 `src/pipeline/bot.js`；HTTP `/api/chat` handler 位于 `src/http/chatHandler.js`，不再与 Bot 文件同名。

`runtime` 上最常用的字段：

| 字段 | 用途 |
| --- | --- |
| `runtime.config` | 当前配置（热更新后会替换） |
| `runtime.logger` | 分级日志，文件里保留 debug |
| `runtime.store` | 会话、消息、摘要、人物卡、事件 |
| `runtime.llm` | 模型客户端 |
| `runtime.bot` | 聊天主管线实例（实现见 `src/pipeline/bot.js`） |
| `runtime.chat` | 唯一聊天门面：`handle()` / `stream()` |

| `runtime.plugins` | Wasm/JS 插件运行时 |
| `runtime.capabilities` | `invokeHost()` 分发宿主能力；`invoke()` 编排插件 provider，两者共享注册表但调度路径不同；`hostStats()` / `hostGlobalStats()` 提供只读统计，`close()` 关闭准入 |

## 4. 主链路 A：微信消息 → 回复 → 发出去

这是最常查的一条线，按调用顺序：

1. **桥接收消息**：`bridge/receiver_mixin.py` 的 `on_message()` → 批次/合并 → `flush_chat()` → `on_message_inner()`。
2. **桥接调内核**：`on_message_inner()` 组 payload，`POST {bot_url}/webhook/wechat`，带 `x-whale-bridge: 1` 和 `x-bot-token`。
3. **HTTP 入口**：`src/http/routes/bridge.js` 的 `/webhook/wechat` → `gateway.handleInbound(body, {local:true})`。
4. **网关归一化**：`src/adapters/gateway.js` 的 `normalizeInbound()` 把桥接字段变成统一的 `msg`（`chatId/chatType/senderId/text/atMe/...`）。
5. **聊天门面**：`runtime.chat.handle(msg)`（`src/app.js`）。无 `chat.handle@1` 接管 provider 时调用 `Bot.handle()`，由 Bot 的会话队列串行；有接管 provider 时先经 `Bot.queueSession()`，再调用 `runtime.capabilities.invoke('chat.handle@1', ...)`，通过前置闸后执行插件，并由宿主完成结果治理。宿主能力 `invokeHost()` 的准入池不代替这条聊天队列。
6. **Bot 主流程**：`Bot.handle()` → `_handleOnce()` → `decide()` → `_decide()`。
7. **决策**：`_decide()` 依次做触发判断、插件 hook、记忆检索、提示词装配、模型调用或固定话术。
8. **生成**：`_handleOnce()` 调 `llm.complete({system, turns})`；失败会走半窗/备用服务商/精简重试。
9. **回复整形**：`transformPluginReply()`（`chat.reply`、`chat.before_send` hook）→ `finalize()`（清标记、去脏话、截断、拆气泡）。
10. **回桥接**：网关把 `{action:'reply', reply, bubbles, mention}` 作为 HTTP 响应返回；`bridge/receiver_mixin.py` 读 `reply/bubbles`，决定文字还是语音。
11. **真正发送**：`bridge/sender_mixin.py` 的 `send_text()`：优先后台通道 `bg_sender`，再退 UIA / 键盘 / OCR。

网关每轮预算：`Gateway.handleInbound()` 按 `config.chat.turnTimeoutMs`（默认 120000，0=不限，负数/非数字回落默认，上限 600000）为每次入站创建独立 `AbortController` 与 deadline，并在 `finally` 清掉 timer；该 signal/deadline 传给 `runtime.chat.handle`（或嵌入式 `Bot.handle`），下游按同一个 signal 协作式退出。它是单轮超时信号，不是 HTTP 连接断开信号：客户端断开仍不会取消本轮。

桥接送进来的 payload 关键字段：

```json
{
  "chat_id": "wxid_xxx 或 xxx@chatroom",
  "chat_type": "private 或 group",
  "sender_id": "wxid_sender",
  "senderName": "昵称",
  "text": "消息正文",
  "msg_id": "username:shard:local_id",
  "at_me": true,
  "mentioned_names": [],
  "self_names": [],
  "chat_title": "群名"
}
```

## 5. 提示词是怎么拼出来的

两个函数决定一切：

- `src/persona/prompt.js` 的 `buildPromptParts()`：拼 **system** 和本轮 **tail**。
- `src/core/context.js` 的 `buildTurns()`：拼 **历史对话 + 当前消息 + 记忆块 + tail**。

`buildPromptParts()` 固定返回静态 system 与本轮 tail；tail 始终与历史/记忆一并落在最后一条 user turn。

`buildTurns()`：

- 私聊：历史按 `user` / `assistant` 逐条；当前消息单独一条 `user`。
- 群聊：历史事件 JSON 行 + 当前消息 JSON 压进一条 `user`，带发言人哈希标签。
- 记忆块（人物卡/事件/摘要/关系卡）和 `tail` 都拼到最后一条 `user` 后面，避免打断 system 前缀缓存。

模型请求由 `src/llm/client.js` 的 `buildPayload()` 组装：

```json
{
  "model": "配置的模型",
  "messages": [
    {"role":"system","content":"system 文本"},
    {"role":"user","content":"历史/当前消息"},
    {"role":"assistant","content":"历史回复"},
    {"role":"user","content":"当前消息 + 记忆 + 本轮状态"}
  ],
  "stream": false
}
```

`complete()` 负责重试、思考参数降级、空响应处理；返回 `choices[0].message.content`，并剥掉思考片段。

## 6. 回复怎么回到微信

本地桥接模式没有 `outboundUrl`，网关不另外 POST，而是把结果放在 `/webhook/wechat` 的 HTTP 响应里：

```json
{
  "ok": true,
  "action": "reply",
  "reply": "整段最终文本",
  "bubbles": ["气泡1", "气泡2"],
  "mention": "要 @ 的人",
  "sticker": {"...": "可选"},
  "separateText": true
}
```

桥接侧：

- `receiver_mixin.py` 读 `reply` / `bubbles`，按 `sendBubbles` 逐条发。
- 群里 `mention` 有值时先尝试 `send_at()`，失败退回普通文本。
- 语音由 `voice_reply.choose()` 决定；失败回退文字。
- `sender_mixin.py:send_text()`：先 `bg_send`（零焦点），失败走 UIA；UIA 不可用再走键盘/OCR。

外部网关模式：`gateway.send()` 把 `{platform, chat_id, chat_type, text, bubbles, reply_to, bot, ts}` POST 到 `gateway.wechat.outboundUrl`。

## 7. 启动器 / 设置链路

- 所有页面用 `launcher/Api.cs` 统一调 `http://127.0.0.1:端口/api/*`，不各自建 HttpClient。
- 保存配置：页面 → `POST /api/config` → `src/http/routes/config.js` → `configPatch` 校验/写盘 → 热更新 `runtime.config`。
- 人设：页面 → `/api/persona` → `src/services/persona.js` → `persona/store.js` 写 `data/persona.json`。
- 状态/诊断：`/api/status`、`/api/debug/*`、`/api/bridge/heartbeat`。`/api/status` 的 `hostDispatch` 字段直接返回 `runtime.capabilities.hostStats()` 的按能力快照（没有分发器时为空对象），不含输入或正文。
- 启动器不直接跑聊天；它只负责启动内核、桥接和展示状态。

## 8. 插件链路

入口在 `Bot.decide()` / `_handleOnce()` / `transformPluginReply()`：

1. `chat.received`、`chat.pre_reply`：消息进入时，插件可 skip/wake。
2. `chat.prompt`：可改 `system`。
3. `chat.generate`：可直接给文本，跳过正常模型生成。
4. `chat.reply`：生成后、finalize 前改写。
5. `chat.before_send`：发送前最后改写。
6. `chat.dispatched`：网关发送后通知。

实现分层：

- `src/services/unifiedPluginRuntime.js`：统一协议插件执行、授权代次与进程回收。
- `src/services/unifiedCapabilityDispatcher.js`：`invoke()` 负责 provider 编排、替换冲突与定时任务；`invokeHost()` 负责宿主能力 schema/授权校验、每能力独立准入与跨能力全局额度（每能力默认 32 并发、128 等待、最多等待 30 秒；全局 `maxHostTotalConcurrent` 默认 512、允许 1–8192，达到上限快速报 `host_capability_queue_limit` 并记 `globalRefused`）。等待可取消/超时，入场前复核授权；`priority`（-100–100，默认 0）只重排尚未开始的等待者，同优先级 FIFO。运行中的 handler 不被强杀，真实结束后才释放名额。活动上下文内的嵌套 `invokeHost` 继承父 deadline（取较小值，不扩张）与取消来源：父 frame 记的是来源 signal 集合，子调用重新订阅并在 settle 时释放，因此中间层先结束也不切断后代的取消链；祖先是否被继承，只看调用发起时链上还有没有 `active` 祖先——只要更上层还在跑，延后发起的调用就仍继承它，只有当前不存在任何活动祖先时才不继承。继承只在同一 dispatcher 的活动宿主上下文中生效，不跨进程，也不覆盖 `invoke()` provider 编排路径。
- 统计与诊断：`hostStats()` 按能力给出 `active`/`waiting` 实时值与 `granted`/`completed`/`failed`、`refused`/`refusedByReason`、`idempotentHit`、`queueFull`/`nestedRefused`/`queueTimeout`/`queueAborted` 累计值；`hostGlobalStats()` 给出 `active`/`globalRefused`/`refused`/`refusedByReason`。准入前拒绝按原因入桶，未登记名字只进全局 `unknown`；`/api/status` 的 `hostDispatch` 透出按能力快照。真队列满的 debug 日志为 `[host-admission] queue_full capability=… active=… waiting=…`，嵌套满池带 `phase=nested`、全局额度拒绝带 `phase=global`，只含能力名与计数。
- 幂等与持久任务：写能力可传 `idempotencyKey`（1–128 字符，能力+调用者+键，5 分钟/256 条，进程内）；同键已完成直接复用、在途等待同一 promise，命中只计 `idempotentHit`，不能绕过撤权/禁用。`createRuntime()` 在数据目录可用时把 `data/host-tasks.jsonl` 挂到 `attachDurableStore()`；`submitDurable()` 先落盘再执行，成功或不可重试错误清除、准入失败保留，启动后异步 `replayDurable()` 串行重放。幂等缓存不跨进程，重启重放仍可能再次执行已产生副作用的 handler。
- 隔离执行与关闭：`defineHost(name, handler, { isolate: { module, exportName } })` 让该 handler 经 `src/services/isolatedRunner.js` 在 worker 执行，错误码为 `isolated_timeout`/`isolated_failed`/`isolated_output_limit` 或 `capability_aborted`，仍计入该能力 `failed`；普通 handler 仍是合作式取消。`server.js` 关闭时在停插件前调 `runtime.capabilities.close()`：新调用与排队者立即 `capability_shutdown`，运行中的 handler 允许收尾。
- `src/services/features/index.js`：宿主功能 handler 唯一装配点；HTTP/桥接通过 `features/hostCall.js`，插件通过 `PluginHost.call()`，最终汇合到同一 `invokeHost()`。同一能力内插件与宿主共享容量；这是按能力准入，不是资源域共享池或统一持久化队列。
- `src/services/features/core.js` 的 `search.query@1`：插件与宿主共用的网络读取试用点。预算先按输入 clamp 到 500–30000ms，再用 `deadline - now` 压住并取较小值；剩余预算不足 500ms 时不会被抬回下限，已过期/已取消直接报错且不发起检索，避免“借”回已耗掉的时间。
- 继承的边界：`hostCall(runtime, …)` 与宿主内部直接 `invokeHost` 若位于活动 handler 内可省略 signal/deadline 自动继承；HTTP 入口和普通 Bot 主流程不在宿主上下文里，必须由最外层请求先提供预算。`invoke()` provider 编排路径不写宿主上下文，不要按同一条线理解。**webhook 主线现在由网关给每轮提供 signal/deadline**：`Gateway.handleInbound()` 按 `chat.turnTimeoutMs` 建 `AbortController` 与截止时间并传给 `runtime.chat.handle`，`finally` 清理 timer；但这是单轮超时信号，不是请求生命周期信号——`src/http/routes/bridge.js` 仍不传连接断开的 signal，所以客户端断开不会取消本轮聊天。
- `src/services/pluginRuntime.js`：把两者合成一个门面，`runtime.plugins`。
- `src/services/pluginHost.js`：插件可调用的宿主能力（状态、检索、模型）。
- 完成语义按 `sideEffect` 分级：`none`/`network-read`/`read-*` 在 handler 返回后仍做一次事后取消/超时判定；`local-write`、`external-message`、`external-action`、计费类与任何未知类别只要正常返回就按完成返回，避免调用方按失败重试造成重复副作用。准入与排队阶段的判定不受影响。
- 提醒链路的预算接线（`src/pipeline/bot.js` 的 `tryReminder`）：读能力 `reminders.pendingFor@1` 接 `_decide` 传入的本轮 signal，宿主准入失败（池满/超时）回退 `service.pendingFor`；写能力 `reminders.create@1` / `reminders.cancel@1` **不接 signal**，只带独立 5 秒 deadline，避免中途被掐留下半条状态。`create` 失败仍退回本地 `service.add` 并照常回执，只有本地也失败才回中文错误话术（不含英文错误码）；`cancel` 失败只少算那一条，由「另有 N 条正在发送」如实说明。

## 9. 后台服务与主动消息

- `runtime.scheduler`：日记 tick、记忆快照等进程内定时任务。
- `runtime.capabilities` 启动重放：`createRuntime()` 在下一轮事件循环调用一次 `replayDurable()`，逐条执行 `data/host-tasks.jsonl` 里的持久任务；成功或不可重试错误移除，可重试错误保留，异常只告警、不阻塞启动。
- `runtime.reminders`：提醒队列；桥接定时 `GET /api/reminders/due` 取走并发送，发完 `POST /api/reminders/ack`。
- `runtime.diary`：日记生成/读取。
- `runtime.moments` / `momentsPublisher`：朋友圈读取与发表。
- `src/services/careChat.js`：主动搭话，走 `runtime.chat` 或 `llm.complete`。
- `src/services/digest.js`：消息汇总，用户点「生成」才跑。

## 12. 按症状找入口

| 症状 | 先看 | 再看 |
| --- | --- | --- |
| 微信完全没回复 | 桥接日志、`/webhook/wechat` 是否 200 | `gateway.handleInbound` → `runtime.chat.handle` → `Bot.handle` 的 `reason` |
| 收到但被忽略 | `computeTrigger()` 返回的 `reason` | `Bot._decide` 的静默/范围/去重判断 |
| 回复很慢 | `runtime.llm.complete` 日志 | 提示词预算、联网搜索、重试次数 |
| 搜索提前超时/被判定失败 | `search.query@1` 的 `timeoutMs` 与 deadline | `src/services/features/core.js` 的预算 clamp、`src/services/search.js` 的 `deadline` 派生 |
| 宿主能力报队列满/排队超时 | `hostStats()` 里该能力的 `queueFull` / `nestedRefused` / `queueTimeout` / `queueAborted` | debug 日志 `[host-admission] queue_full …`（嵌套带 `phase=nested`，全局额度带 `phase=global`）；准入前拒绝看下一行 |
| 宿主能力被准入前拒绝 | 该能力 `hostStats().refused` / `refusedByReason` 与 `hostGlobalStats().refusedByReason` | 未登记名字只出现在全局 `unknown`；拿到名额后的失败看 `failed` |
| 全局额度打满 | `hostGlobalStats().globalRefused` | 等待优先级 `priority` 只重排未开始者；运行中调用不会被抢占 |
| 隔离执行的 handler 超时/崩溃 | `isolated_timeout` / `isolated_failed` / `isolated_output_limit` | 该能力 `failed`；`defineHost` 的 `isolate` 配置与执行器测试 |
| 重启后持久任务重复/丢失 | `data/host-tasks.jsonl` 与启动日志「持久任务重放」 | `replayDurable()` 摘要；幂等缓存只在进程内，崩溃窗口可能重放 |
| 关闭服务时调用报 capability_shutdown | `server.js` 关闭流程调 `runtime.capabilities.close()` 的预期结果 | 运行中 handler 允许结束，排队者立即失败 |
| 提醒没设上但回复说失败 | `tryReminder` 的 `writeOptions()`（5 秒 deadline）与本地 `service.add` | `reminders.create@1` 宿主失败后仍应退回本地登记；只有本地也失败才回错误话术 |
| 提示词不对 | `src/persona/prompt.js` | `src/core/context.js`、`data/persona.json`、插件 `chat.prompt` |
| 回复内容被改 | `finalize()` | 插件 `chat.reply` / `chat.before_send` |
| 回复发不出去 | `gateway.send()` | 桥接 `send_text` → `bg_sender` / UIA / 键盘 |
| 设置保存失败 | `POST /api/config` | `configPatch`、`config.json` 是否可写 |
| 插件不生效 | `/api/plugins` 状态 | `unifiedPluginRuntime`、`unifiedCapabilityDispatcher`、`pluginHost` |
| 启动器连不上内核 | `/healthz` | `RuntimeSupervisor.WaitForNodeAsync`、端口文件、日志 |
