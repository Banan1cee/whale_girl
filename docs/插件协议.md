# 鲸鲸插件协议（whale-plugin/1）

本文件是当前唯一在用的插件协议。旧的 Api 1/2/3/4 可执行插件**不再运行**；纯数据人设包继续支持。
协议状态：开发版，随鲸鲸 4.3.0 起提供本地安装与试装；远端市场尚未开放这一代的投稿。

协议分五级：0 级是纯数据主题（`theme-data`，没有执行体、没有能力、不需要授权），1–4 级是可执行插件。
0 级主题是 4.3.0 新增的协议等级，不是旧 Api 的延续。

## 1. 包里有什么

ZIP 根目录只能有 `plugin.json` 和该等级的入口。`level` 是必填整数，不是旧 API 版本号：

| 等级 | 入口与环境 | 允许的能力 |
| --- | --- | --- |
| 0 | `theme.json` / `theme-data` | 无：`provides`、`calls` 必须为空，不执行任何代码 |
| 1 | `plugin.wasm` / `wasm-restricted` | 手动整数工具 `tool.run@1` |
| 2 | `plugin.wasm` / `wasm-restricted` | 手动 UTF-8 文本工具 `tool.run@1` |
| 3 | `plugin.wasm` / `wasm-restricted` | 手动文本工具、经聊天授权的 `chat.reply@1`，可单独申请 `chat.history` / `model.prompt` |
| 4 | `plugin.js` / `node-full` | 现有注册表列出的扩展点和可用宿主调用，须确认完整系统权限 |

0 级主题包只允许 `plugin.json` + `theme.json` 两个文件，入口上限 64 KiB；没有 `plugin.wasm` / `plugin.js`，也没有任何宿主调用。

3 级可在清单写 `dataAccess` 逐项申请读取最近 12 条聊天记录或本轮系统提示词；不申请就不传入，启用时与聊天授权一并确认。运行时按授权记录校验，缺项即拒。1、2 级不得声明 `dataAccess`。

1–3 级的 `calls` 必须为空。受限 Wasm 的输入限于宿主提供的数据，不提供文件、网络、进程、主动发送或 WASI 导入。3 级回复扩展默认收到本轮消息和草稿，额外字段按各插件自己的 `dataAccess` 授权投影。该协议不提供直接读取记忆的接口。等级沿用旧权限分档，旧 API、旧包和按次汇总接口已经停用。

### Wasm 入口

导出 `run() -> i32`。只允许从 `whale_plugin` 导入 `input_size() -> i32`、`input_byte(i32) -> i32`，以及 2–3 级的 `output_byte(i32)`。读取越界返回 `-1`。手动工具收到原样 UTF-8 字符串；其他 JSON 值先编码成 JSON。3 级回复扩展收到 UTF-8 JSON `{input, settings}`。1 级使用 `run` 的整数返回值；2–3 级须返回 `0`，并在 `run` 内逐字节输出 UTF-8。回复扩展输出 `{"text":"…"}` 等符合回复契约的 JSON；手动工具输出文本。每次执行都使用独立的受限 Wasm Worker，仍受宿主预算与撤权约束。

其他文件（README、测试、fixtures）留在作者项目里，不放进安装包。

## 2. 清单

```json
{
  "format": "whale-plugin/1",
  "level": 4,
  "id": "word-count",
  "name": "字数统计",
  "author": "你的名字",
  "version": "1.0.0",
  "minAppVersion": "4.3.0",
  "description": "统计输入文本的字数",
  "entry": "plugin.js",
  "runtime": "node-full",
  "provides": {
    "tool.run@1": { "mode": "tool", "scope": "manual" }
  },
  "calls": ["status.read@1"],
  "settingsSchema": {
    "type": "object",
    "properties": { "maxChars": { "type": "integer", "minimum": 1, "maximum": 10000 } },
    "additionalProperties": false
  },
  "executionTimeoutMs": 30000
}
```

规则：

- 未知字段直接拒绝；`format`、`runtime`、`entry` 必须与上面一致。
- `id` 小写字母开头，只含小写字母、数字和短横线，最长 48。
- `version` / `minAppVersion` / `maxAppVersion` 为三段或四段数字版本。
- 0 级：`level` 为 0，`entry` 固定 `theme.json`，`runtime` 固定 `theme-data`，`provides` 必须是空对象、`calls` 必须是空数组，
  不得声明 `settingsSchema` / `dataAccess`；`minAppVersion` 必填且不得低于 4.3.0（旧启动器不认识 0 级）。
- 兼容宿主代次用 `appEpoch`（1 或 2）或 `appCompatibility` 数组；不写时按旧代（`appEpoch: 1`）比较。
  它只描述「哪个鲸鲸版本能装」，与插件协议版本无关。
- `provides` 至少一项，键必须是下表能力 ID，`mode` / `scope` 必须在该能力允许范围内（0 级例外：必须为空）。
- `calls` 是允许插件回调宿主的能力 ID；没写的能力一律不可调用。
- `settingsSchema` 只接受 `type`、`properties`、`required`、`additionalProperties`、`enum`、`minimum`、`maximum`、`minLength`、`maxLength`、`title`、`description`，根节点必须是 `object`，最大深度 8（0 级不得声明）。
  `title` 最长 40 个字符且不能全空白，`description` 最长 200 个字符；两者只允许字符串，且不能包含控制字符及指定双向文本标记（注册表 `settingsSchema.annotations.forbiddenRanges`）；超长或含禁用字符会被拒绝。
- `executionTimeoutMs` 取值 100–120000，默认 30000。

### 2.1 0 级主题包（`theme.json`）

主题包只描述外观，不描述布局、页面或行为。`theme.json` 是唯一内容，必须与清单 `id` 相同：

```json
{
  "schema": 1,
  "id": "mint",
  "name": "薄荷",
  "author": "你的名字",
  "version": "1.0.0",
  "colors": {
    "accent": "#6FD6C0", "background": "#07120F", "surface": "#101B18",
    "text": "#F2FAF7", "muted": "#9FB3AD", "border": "#243140", "field": "#0C1714"
  },
  "font": { "family": "Microsoft YaHei UI", "scale": 1.05 },
  "metrics": { "corner": 12, "spacing": 1.05 },
  "dialog": { "surface": "#101B18", "border": "#243140", "corner": 12 }
}
```

- 顶层只允许 `schema`、`id`、`name`、`author`、`version`、`colors`、`font`、`metrics`、`dialog`；未知字段整包拒绝。
- `schema` 固定 1；`id` 必须等于 `plugin.json` 的 `id`；`name` 必填，`author` / `version` 可省略。
- `colors` 只允许 7 个语义键：`accent`、`background`、`surface`、`text`、`muted`、`border`、`field`；
  值为 `#RRGGBB` 或 `#AARRGGBB`。`Ok/Warn/Bad` 等安全信号色和顶栏颜色不开放。
- `font.family` 只能取内置白名单（`Microsoft YaHei UI`、`Microsoft YaHei`、`Segoe UI`、`SimSun`）；
  `font.scale`、`metrics.spacing` 为 0.85–1.15；`metrics.corner`、`dialog.corner` 为 0–24。
- 文件上限 64 KiB、严格 UTF-8、JSON 深度 8；启用时再校验最终对比度（正文 4.5、强调色 3），不达标不应用。
- 主题包**不包含页面样式**：`launcher-pages.json` 是启动器本地文件（页面密度/字号与区块显隐），
  不随插件包分发，也不通过市场投稿。主题也不开放布局、导航或安全确认弹窗。
- 0 级没有执行体：安装、启用都不执行代码，不产生授权记录；启用 = 应用外观，停用 = 恢复内置，卸载会一并撤销当前主题。

**校验发生在哪一步（0 级主题）**：作者 CLI 的 `validate` / `test` / `pack` 只检查文件大小、JSON 对象、`schema: 1`、`theme.json.id` 与清单一致和 ZIP 结构；**不检查**颜色、字体白名单、缩放/圆角数值、对比度，也不检查最低客户端版本。这些在启动器侧：安装/读取包时校验 token 白名单与数值、字体、`theme.json` 与清单一致及 0 级最低版本（4.3.0），启用时再按最终配色校验对比度。CLI 通过不等于启动器会接受。
## 3. 扩展点

| 能力 ID | 允许模式 | 允许作用域 | 何时调用 | 数据边界 |
| --- | --- | --- | --- | --- |
| `tool.run@1` | `tool` | `manual` | 用户在插件卡片点「运行一次」 | 任意 JSON 输入、JSON 输出 |
| `chat.handle@1` | `replace` | `all` | 收到消息、宿主安全闸通过后 | 当前消息；只能返回回复或忽略 |
| `chat.generate@1` | `replace` | `all` | 本轮需要生成回复时 | 当前消息、system、turns；返回文本 |
| `chat.reply@1` | `observe` / `enhance` / `replace` | `all` | 生成出草稿之后、发送之前 | 当前消息与草稿文本；返回新文本 |
| `chat.search@1` | `replace` / `enhance` | `all` | 本轮需要联网资料时 | 当前消息；返回结构化检索结果 |
| `task.tick@1` | `schedule` | `all` | 宿主按清单 `intervalSeconds` 触发 | `{scheduledAt, now, settings}` |

`observe` 只读：返回值被丢弃。`enhance` 收到前一层有效结果，返回替换值。`replace` 同一能力同一作用域
只能有一个提供者，冲突在调用任何插件之前返回 `capability_owner_conflict`。

接管 `chat.handle@1` 时，以下情况仍由宿主先处理并直接返回，不进入插件：管理员魔咒、禁言/白名单、
重复消息。插件返回 `{action:'reply', reply, bubbles?, mention?}` 后，宿主仍会做发送范围检查。

### 3.1 输入输出实例（与注册表 schema 对齐）

只保留同名 provider 不够：实现必须满足注册表的 `inputSchema` / `outputSchema`、模式和作用域，否则宿主在调用前/后直接拒绝。以下是各扩展点的最小真实形状（字段可省略的按 schema 规定，未知字段会被拒绝）。每段代码都是独立、可直接复制的 JSON。

**tool.run@1**（任意 JSON，手动运行）

输入：

```json
{
  "text": "你好"
}
```

输出：

```json
{
  "characters": 2
}
```

**chat.handle@1**（全接管，replace）

输入：

```json
{
  "localWechat": true,
  "message": {
    "platform": "wechat",
    "chatType": "private",
    "chatId": "wxid_demo",
    "senderId": "wxid_demo",
    "senderName": "主人",
    "text": "在吗",
    "atMe": false,
    "msgId": "1001",
    "chatTitle": ""
  }
}
```

回复：

```json
{
  "action": "reply",
  "reply": "在的",
  "bubbles": ["在的"],
  "mention": ""
}
```

忽略：

```json
{
  "action": "ignore",
  "reason": "not_for_me"
}
```

`reply` 必填且非空；`bubbles` 只是建议，宿主仍会做气泡拆分、群聊输出兜底与字数上限，**不会直接下发**；`mention` 是否真正 @ 到人由桥接发送结果决定。

**chat.generate@1**（替换本轮模型生成）

输入：

```json
{
  "message": {
    "platform": "wechat",
    "chatType": "private",
    "chatId": "wxid_demo",
    "senderId": "wxid_demo",
    "text": "在吗"
  },
  "system": "你是鲸鲸。",
  "turns": [
    { "role": "user", "content": "在吗" }
  ]
}
```

输出：

```json
{
  "text": "在的"
}
```

**chat.reply@1**（observe / enhance / replace）

输入：

```json
{
  "message": {
    "platform": "wechat",
    "chatType": "private",
    "chatId": "wxid_demo",
    "senderName": "主人",
    "text": "在吗"
  },
  "text": "在的"
}
```

输出：

```json
{
  "text": "在的呀"
}
```

**task.tick@1**（宿主定时触发）

输入：



## 4. 入口与宿主调用

```js
exports.providers = {
  'tool.run@1': async (input, { host, settings, signal }) => {
    const status = await host.call('status.read@1', {});
    return { chars: [...String(input.text || '')].length, version: status.version };
  },
};
```

- `providers` 的键必须与清单 `provides` 一致；别用旧接口的 `hooks` / `run` / `onHook` 别名。
- 站内调用只允许当前这次执行发起，且必须是清单 `calls` 里声明、宿主已启用的能力。
- 宿主能力：完整清单（输入、输出、副作用、是否需要授权、是否对插件开放）见 本节的《宿主能力全表》，
  唯一事实源是 `src/services/pluginProtocolRegistry.json`；`levels.4.calls` 就是插件可声明的白名单。
  宿主内部（HTTP 路由、桥接取件、定时任务）和插件 `host.call` 走同一个分发器：
  `runtime.capabilities.invokeHost(能力名, 输入)`。按用途分：

| 类别 | 能力 ID |
| --- | --- |
| 只读状态 | `status.read@1`、`settings.read@1`、`features.read@1`、`persona.read@1`、`plugins.status@1`、`wechat.status@1`、`bridge.status@1`、`care.decide@1`、`digest.status@1`、`diary.status@1`、`reminders.list@1`、`reminders.rules@1`、`stickers.status@1`、`moments.latest@1`、`moments.snapshot@1`、`moments.settings@1` |
| 读隐私数据（需授权） | `memory.recent@1`、`memory.recall@1`、`diary.read@1`、`contacts.search@1`、`contacts.list@1`、`contacts.get@1`、`moments.request@1`、`moments.action@1`、`moments.result@1` |
| 写 / 外部动作（需授权） | `reminders.create@1`、`reminders.cancel@1`、`memory.write@1`、`persona.write@1`、`settings.write@1`、`stickers.enqueue@1`、`message.send@1`、`moments.publish@1` |
| 计费模型调用（需授权） | `diary.generate@1`、`digest.generate@1`、`search.query@1`、`model.complete@1` |

- `message.submit@1` 是保留能力，`enabled: false`：可以写进清单方便将来升级，但运行时不会执行，
  UI 会标成「宿主未开放」。发送请用 `message.send@1`（排队到宿主发送通道，语音用 `delivery:'voice'`）。
  `queued` / `submitted` / `confirmed:false` 都不等于微信已送达。
- 宿主能力没有「唯一所有者」：同一项能力可以被任意多个插件同时声明和调用，各自按自己的授权判定；
  这与 provider（`chat.reply@1` 等）的替换名额限制是两回事。


## 4.1 宿主能力全表（仅 4 级）

下面是注册表 `src/services/pluginProtocolRegistry.json` 的文档视图：输入输出、副作用、是否需要授权、是否对插件开放。启动器与作者 CLI 都按同一份注册表校验；4 级插件只能在清单里声明本表「插件可调」为「是」的能力。
##### 分发模型：宿主能力没有唯一所有者

宿主在内部登记能力，插件只通过 `host.call` 使用；宿主内部调用不经过插件授权。

- **宿主内部调用**（HTTP 路由、桥接取件、定时任务）传 `plugin = null`，只校验输入输出；
- **插件调用**传插件对象，额外校验「授权有效 → 清单已声明 → 能力已开放」；
- 同一个宿主能力可以被**任意多个插件同时声明和调用**，不存在谁先登记谁独占，
  也不会像 provider（`chat.reply@1` 等）那样有「唯一所有者/替换名额」限制；
- 宿主实现按领域拆分，HTTP 路由只保留传输层；插件只需按本协议调用，不需要阅读宿主源码。

**失败码：先分「插件可见」与「宿主诊断」**

Node 4 级 Worker 的实际反馈是：大多数宿主实现错误、参数/返回校验错误会被统一折叠成 `host_call_failed`；撤权和超时可能直接终止本次调用，插件未必能 catch 到原始分发器错误码。**不要按内部码分支，也不要在失败后盲目重试。**

插件在 `host.call` 返回里能看到的码（`ok:false`）：

| 码 | 含义 | 建议处理 |
| --- | --- | --- |
| `host_capability_disabled` | 能力已登记但被宿主关闭（如 `message.submit@1`） | 不重试，提示用户 |
| `host_capability_not_declared` | 清单 `calls` 或授权里没有这个能力 | 改清单并重新授权 |
| `host_call_limit` | 本次调用的并发/次数超过上限 | 减少调用或拆批次 |
| `host_input_limit` / `host_output_limit` | 输入或输出超过 512 KiB | 缩小数据 |
| `host_capability_unavailable` | 已登记但宿主没有装配实现 | 视为不可用，不要重试 |
| `host_call_failed` | 其它宿主调用失败（内部码见下） | 按一次普通失败处理，不按内部码分支 |

可能直接终止本次 invocation、未必能以返回值形式捕获的码：

| 码 | 含义 |
| --- | --- |
| `grant_revoked` | 授权已撤回或代次变化 |
| `capability_timeout` | 超过调用时限 |
| `invalid_plugin_ipc` | Worker 与宿主的调用消息不合法 |
| `plugin_error` | 插件自身抛错或返回不合契约 |

宿主诊断码（分发器内部使用，插件通常只会看到 `host_call_failed`；写日志或排查时参考，不要用于业务分支）：

| 码 | 含义 |
| --- | --- |
| `host_capability_unknown` | 注册表里没有这个能力名 |
| `invalid_host_capability_input` / `invalid_host_capability_output` | 输入/输出不符合注册表 schema |
| `capability_aborted` | 调用被取消 |
| `plugin_required` | 该能力只接受插件上下文（目前只有 `message.send@1`） |
作者工具和启动器都从同一份注册表生成能力目录；本文的表格就是它的视图，不需要另行阅读宿主源码。

##### 完整能力表

「插件可调」= 在 4 级 `calls` 白名单里且 `enabled:true`。
标 **内部** 的能力只给宿主/桥接用，插件清单写不进去（不在 4 级 `calls`）。

以下是**真的还没做**的，别按「已经能用」来写插件：

- **启动器里的能力浏览/授权详情界面**：宿主能生成能力目录，但启动器还没有展示某个插件到底用了哪些能力的界面。
- **插件市场投稿/上架**：远端 `Banan1cee/whale-girl-plugins` 还没有 `index-v5.json`，

- **插件自定义界面**：插件不能自行增加左侧入口或页面；可交互的只有 `tool.run@1` 的手动运行。
- **`message.submit@1`**：保留能力，`enabled:false`，声明了也不会执行；发送请用 `message.send@1`。
- **跨会话/跨账号的数据搬运**：`memory.recall@1` 只查指定 chat，联系人只读缓存副本，

## 5. 授权、执行与撤销

- 安装不执行任何代码，也不产生授权。
- 0 级纯数据主题没有执行体：安装与启用都不签发授权、不占执行 Worker，也不经过内核或插件总开关；启用/停用只切换启动器外观。
- 3 级回复扩展启用时须确认聊天访问；4 级启用时须确认完整系统权限。授权记录绑定等级、插件 ID、安装包摘要、入口摘要、授权代次、
  批准的 provider 列表与 call 列表、设置快照。
- 修改设置即重签授权；旧代次的在途调用结果会被丢弃。
- 停用/更新会撤销授权、终止受管理的 Worker；已经发生的外部副作用无法撤回。
- 每次调用有超时预算，排队时间计入预算；超时、取消、撤权都会拒收迟到结果。
- 同时最多 2 个 Worker、最多 16 个已安装插件、单次输入输出 512 KiB、单份设置 64 KiB。
- 失败返回稳定错误码：`invalid_capability_input`、`invalid_capability_output`、`capability_owner_conflict`、
  `capability_not_declared`、`capability_timeout`、`capability_aborted`、`grant_revoked`、
  `host_capability_not_declared`、`host_capability_disabled`、`plugin_error`。

**Node 插件不是沙箱。** 它以自己的 Windows 用户身份运行，可以读写文件、联网、启动其他进程；
`calls` 只约束「宿主代为执行的能力」，不能限制代码本身。只启用信任的作者。

### 5.1 重写与重构时的兼容边界

- **对外必须保持**：插件入口与包结构、能力名与输入输出 schema、模式/作用域、授权与确认语义，以及旧设置/旧插件数据继续可读。透明的重写/重构在「授权未撤回、安装包与设置都不变」的前提下，不得要求用户重新授权；一旦撤权、换包或改设置，仍按现有规则重新确认。
- **内部可随版本改**：宿主内部 IPC、调度实现、进程/Worker 机制不构成插件 API，可以与宿主一起改；但不能把跨调用状态隔离等内部实现细节变成可观察变化。外部行为、触发时机、重试与错误语义不得静默改变；入队/排队不等于已送达，不得因重写改变这一语义。插件也不应依赖内部消息格式。
- **内部 HTTP 不是 SDK**：`/api/*`、`/api/plugins/run` 等只服务启动器、桥接和宿主自身，不承诺对插件兼容；插件只依赖本协议与 `host.call`。

## 6. 作者工具

```text
npm run plugin -- init my-tool --template tool
npm run plugin -- validate my-tool
npm run plugin -- test my-tool
npm run plugin -- pack my-tool --out dist/my-tool.zip
npm run plugin -- trial dist/my-tool.zip
```

- `validate` / `test` / `trial` 都是静态检查，不执行插件代码；`test` 做 CommonJS 语法或受限 Wasm 模块检查。
- 0 级主题用 `validate` / `pack` 做静态 JSON 与 ZIP 检查；`init` 没有主题模板，手动创建 `plugin.json` + `theme.json` 后打包。
- `trial` 输出模拟结论：`executed`、`installed`、`authorizationGranted` 都是 `false`，
  只展示路由、需要确认的权限和宿主未开放的能力。
- `pack` 生成根目录只有 `plugin.json` 和该等级入口（1–3 级 `plugin.wasm`、4 级 `plugin.js`、0 级 `theme.json`）的 ZIP。

模板位于 `templates/plugins/`：`integer-tool`、`tool`、`reply-wasm`（1–3 级 Wasm）与 `reply-enhancer`、`chat-takeover`、`scheduled-task`（4 级 Node）。`npm run plugin -- init <id> --template <模板>` 会按模板等级生成对应入口。

## 7. 安装、更新与卸载

- 启动器「插件市场 → 从本地安装」选择 ZIP；确认框会显示提供者、版本、声明的 provider、calls 和作者变化。
- 0 级主题安装后在「已安装」卡片里启用/停用/卸载：启用 = 应用外观，停用 = 恢复内置，卸载会先撤销当前主题；不需要打开插件总开关，也不需要启动内核。
- 旧版独立 `data/launcher-theme.json`会在免责声明放行后登记为 0 级主题插件（`legacy-theme-<视觉摘要前 8 位>`）。现有外观数据保留在主题快照中，快照同时记录选中的插件 ID，重复打开不会重复迁移。
- 首次进入插件市场必须先阅读页内免责声明：全文滚到底并停留满 10 秒才能确认，确认与正文摘要一起保存到本机；正文更新后旧确认自动失效，需要重新阅读。
- 在插件卡片启用：1–4 级都会写入授权记录；1–2 级没有额外权限弹窗，3 级仅在声明 `chat.reply@1` 时确认聊天访问，4 级确认完整系统权限。插件总开关（`features.plugins`）默认关闭。此前未声明 `level` 的开发版包须更新清单、重新打包并重新授权，不会被自动升为 4 级。
- 同一 ID 更新必须升版本、保持作者一致；更新后需要重新启用，设置保留，授权重新签发。
- 卸载会删除包文件、授权、设置与该插件的会话状态。

## 8. 投稿

远端 `Banan1cee/whale-girl-plugins` 目前仍只发布人设目录与旧 Api 1–4 目录，**没有**新协议的
`index-v5.json`。所以现在只能本地安装试装；投稿校验、目录生成和 CI 需要市场仓库同步后才会开放，
不能因为本地安装成功就认为已上架。0 级主题同样只支持本地安装，市场目录暂不收录主题，也没有主题投稿通道。

## 9. 旧启动器兼容

- 0 级主题要求 4.3.0 及以上：旧启动器不认识 `level: 0` / `theme-data` / `theme.json`，会拒绝安装或标记版本不兼容。
- 页级样式 `launcher-pages.json` 只由启动器读取，旧启动器忽略该文件，默认外观与顺序不受影响。
- 新启动器仍能读入旧格式 `launcher-theme.json`。迁移后的快照包含插件 ID，旧启动器无法读取这一新格式。
