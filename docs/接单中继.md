# 接单中继（relay）：前台 AI + 干活 agent

> 状态：实验特性，不走启动器 UI。只做「微信接单」这一条链路，不替代内核的鲸鲸人格、记忆和关怀系统。

## 1. 为什么要有这一层

内核（`src/`）是一个聊天机器人：固定人设、按会话记忆、单次请求单次回复。它可以陪聊，但不能替人把项目接下来——
接单要的是「问清需求 → 汇总给干活的人 → 盯进度 → 把结果和问题转述给客户」，这是一个跨多轮、跨角色的流程。

`relay/` 就做这件事：它顶替内核的位置接住桥接（`bridge/`）的 webhook，用两个 DeepSeek Harness 会话分别扮演
**前台**（对客户）和**工人**（对项目），中间只传自然语言。

```
客户 ──微信──> bridge/ ──POST /webhook/wechat──> relay
                                                 │
                                                 ├─ dsh headless（前台 session，一个客户一个）
                                                 └─ dsh headless（工人 session，一个订单一个）
```

桥接侧一行代码都不用改：它只认 `WHALE_BOT_URL`，把地址指过来即可。

## 2. 两个角色

| | 前台 AI | 干活 agent |
|---|---|---|
| 用谁的模型 | DeepSeek Harness session（`desk`） | DeepSeek Harness session（`worker`） |
| 对谁说话 | 客户 | 前台 |
| 记忆 | 按会话粘住，跨订单延续 | 按订单粘住，跨轮次延续 |
| 权限 | 只读都能跑，不给工具也无所谓 | 只在自己的订单工作区里读写 |
| 能承诺什么 | 只承诺订单档案里写过的东西 | 不面向客户，随便说 |

人格隔离靠的是**位置**，不是模型自觉：工人没有通往客户的通道，它的输出必须经前台重写一遍才可能发出去。

## 3. 订单档案是唯一事实来源

`relay/state/orders/<orderId>/order.md` 里的【需求】【验收】【口径】三节，前台每轮都读，工人每轮也读。
客户新说的要求由前台用【需求更新】标出来，中继追加进去。这意味着：

- 客户改需求 → 档案变 → 下一轮工人看到的就是新档案，不需要谁去「同步上下文」。
- 老板要核查一单 → 看 `order.md` + `thread.md` 就够，不用翻聊天记录。
- 价格、工期这类不能让 AI 随口承诺的东西，写在【口径】里，前台被明确要求只按口径说。

## 4. 一轮消息里发生什么

```
1. 收到 webhook → 去重（msg_id）→ 同会话排队
2. 取订单（没有就建）
3. 前台轮：档案 + 客户原话 → 【回复客户】/【派单】/【需求更新】
4. 有【派单】（或工人在等客户回答）→ 工人轮 → 【给前台】/【需要确认】/【产出】
5. 前台再跑一轮，把工人汇报翻成客户听得懂的话
6. 只把最后那段的【回复客户】发回桥接
```

没有 JSON 协议：前台和工人之间就是自然语言，三个【标记】只是给中继分流的**路牌**。模型漏写标记时，
整段话会被当成回复发出去（宁可多说一句，不能丢消息）；写了标记但缺【回复客户】时，中继用兜底话术顶上。

## 5. 订单状态与放行闸门

`intake`（谈需求）→ `working`（工人干活）→ `delivered`（已交付）。

`intake → working` 这一步是钱和责任的边界，所以由配置决定谁来放行：

- `orders.confirmMode: "frontdesk"`：前台判断需求够了就派单。用于演示与内部试用。
- `orders.confirmMode: "owner"`：前台只能谈，派单会被拦下；老板在微信里发 `#确认 ord-...` 才开工。生产必须用这个。

老板指令（只认 `owner.chatId` 那个会话）：`#确认 [订单号]`、`#完成 [订单号]`、`#暂停`、`#恢复`、`#状态`。

## 6. 在 DeepSeek Harness 里看会话

前台和工人都是真实的 DSH 持久 session，落在 `~/.dsh/sessions/<工作区目录名>/session-<id>/`：

- 前台会话的工作区是 `relay/state/desk`；
- 工人会话的工作区是该订单的 `relay/state/orders/<orderId>/workspace`。

在桌面端对应工作区里打开 session，就能看到完整的用户消息、思考、工具调用和输出——和平时看自己的会话一样。
日志目录 `relay/state/orders/<orderId>/worker.jsonl` 里还有工人每一轮的原始 NDJSON 事件，用于排查。

## 7. 已知边界（先说清楚，免得后面踩）

1. **回复只能同步返回**。桥接没有异步推送通道，回复必须在 webhook 的 HTTP 响应里带回；一轮干活超过
   `worker.timeoutMs`（默认 10 分钟）时，这一轮按失败处理，前台会先安抚客户。要真正的「做完再发消息」，
   需要给桥接加一个 outbox 接口（改动很小，但属于桥接改造，单独评估）。
2. **个人微信不是官方接口**。账号风险由使用方承担，v1 只建议白名单客户 + 测试号。
3. **串行发送**。桥接每次只能发一条，多客户同时说话会排队；`PIPELINE_WORKERS` 决定并发上限。
4. **成本**。一条客户消息可能触发 1~3 次完整 DSH 轮次；建议开局就把 `worker.timeoutMs` 和订单预算设小，先跑小单。
5. **DSH session 存 `~/.dsh`**，换机器或清空该目录等于丢记忆；订单档案和对话另有 `relay/state` 落盘，可重建上下文。
