# 我在微信里养了个 AI 群友：零焦点 UIA 收发、本地数据、可换人设

> 一句话：不修改微信客户端、不注入、不联网中转，在 Windows 上把一个会聊天、能发语音、有长期记忆的 AI 塞进你自己的微信号里。
>
> 项目地址：<https://github.com/Banan1cee/whale_girl> （AGPL-3.0-only）
> 下载：<https://github.com/Banan1cee/whale_girl/releases>

---

## 一、为什么做这个

市面上的"微信 AI"基本都是三种：客服机器人（关键词 + 菜单）、SaaS 托管号（消息走别人服务器）、或者干脆是模拟器挂机。

我想要的不是这些。我想要的是**群里那个会接梗、会顶嘴、偶尔说话有意思的朋友**——她的回复要符合人设、要看得到上下文、要能记住昨天聊过什么，而不是每条都回一句"好的呢～"。

所以整个项目的第一条设计原则是：**她得像群里的人，而不是像客服。** 这条原则后来变成了具体的工程取舍：提示词分层、记忆预算、回复长度上限、群聊插话概率，全都是为它服务的。

第二条原则是**数据不出本机**：消息、记忆、API Key 全在用户自己的电脑上，程序不开公网端口，也不需要任何后端。

## 二、整体架构

三层，职责切得很干净：

```
┌──────────────────────────────┐
│ WPF 启动器 (launcher/)        │  安装、配置、诊断、一键启停
│   .NET 10 / 单文件 exe        │  人设预设、朋友圈、桥接控制台
└──────────────┬───────────────┘
               │ 启动/重启子进程
┌──────────────▼───────────────┐
│ Node 内核 (src/, server.js)   │  提示词、记忆、联网、多平台适配
│   HTTP 127.0.0.1:8787         │  无第三方依赖，纯标准库
└──────────────▲───────────────┘
               │ HTTP（本机，带 token）
┌──────────────┴───────────────┐
│ Python 桥接 (bridge/)         │  UIA 认窗、收发消息、语音、朋友圈
│   wechatauto + pywin32        │  独立进程，崩了不影响内核
└──────────────┬───────────────┘
               │ 只读 SQLite / 窗口消息
        ┌──────▼──────┐
        │ 微信 4.x     │
        └─────────────┘
```

**为什么拆成三层？**

- 桥接要调 Windows 的 UI Automation、要解密微信本地数据库，这些在 Python 生态里最成熟；但 Python 的异步和并发在"同时处理 4 个会话 + 语音合成 + 图片识别"这种场景下很难写对。
- 内核是纯 Node 标准库实现，零 npm 依赖——安装包不用 `node_modules`，升级也不会被依赖版本坑。
- 启动器是 WPF，负责一切"用户会点到的界面"：它同时是内核和桥接的父进程，**用 Job Object 绑住子进程**，所以正常关闭、崩溃、被任务管理器强杀，内核和桥接都会被一起收掉（以前会留孤儿进程占着端口，下次启动直接冲突）。

## 三、最难的部分：怎么"不抢前台"地收发消息

这是整个项目 80% 的坑所在。

### 3.1 收消息：直接读本地数据库

微信 4.x 把消息存在本地 SQLite 里（`xwechat_files/<账号>/db_storage/`），有新消息时会有 WAL 写入。

桥接的做法是**只读打开数据库**，轮询消息表：

```python
# bridge/wechat_db.py（简化）
rows = db.get_messages(chat_username, limit=12)
for m in rows:
    content = m.get("content") or ""
    # 文本直接用；图片/表情/语音走各自的识别链路
```

好处是不碰进程内存、不 hook、不需要注入；坏处是**必须能找到数据目录**。这就是我们踩得最多的坑：

- 用户的微信文件目录可能在任意盘（`E:\xwechat_files`、`D:\微信聊天\xwechat_files`……）
- 也可能在用户目录下（`C:\Users\xxx\Documents\xwechat_files`），**不在盘根**
- 早期版本只扫盘根，于是大量用户报"桥接说一个账号都没有"

现在自动探测的顺序是：配置手填 → 微信进程打开的文件句柄 → 常见文档目录 → 盘根扫描，任何一步失败都会在日志里明确提示"请去设置页填微信文件保存位置"，而不是让用户对着"找不到账号"发呆。

### 3.2 发消息：窗口消息打字 + 点发送按钮

这是最反直觉的一块。想"不抢前台"地发消息，不能用剪贴板（会抢焦点），也不能用 `SendKeys`（同上）。

我们的做法是**给微信窗口的输入框发 `WM_CHAR`**，然后模拟点一下发送按钮：

```python
# bridge/bg_sender.py（简化）
def encode_utf16(text):
    """微信 4.2 起 WM_CHAR 的 wParam 不再当 GBK 字节解释，而是当字符码。"""
    data = str(text or "").encode("utf-16-le", "surrogatepass")
    return [int.from_bytes(data[i:i+2], "little") for i in range(0, len(data), 2)]

for unit in encode_utf16(text):
    win32gui.PostMessage(hwnd_edit, win32con.WM_CHAR, unit, 0)
    time.sleep(char_gap_ms / 1000)
```

这里有个实际踩了很久的坑：**编码语义随微信版本变**。

| 微信版本 | `WM_CHAR` 的 wParam 语义 | 发 GBK 字节会怎样 |
|---|---|---|
| 4.1 及以前 | GBK 双字节 | 正常 |
| 4.2+ | 单个字符码 | 中文变成 `¾¨¾¨` 这种乱码 |

所以发送通道里做了版本探测，配置项 `wechat.bgSend.charMode` 可以强制 `utf16` / `gbk` / `auto`。遇到中文发出去是乱码的用户，改这一个值就好了。

### 3.3 认窗：同一台机器有多个微信窗口时

电脑上双开、或者微信最小化到托盘再打开，会同时存在 2~3 个候选窗口。点错窗口的后果很严重（消息发到别人那里），所以我们用**打分选窗**而不是"取第一个"：

```python
# bridge/uia_boot.py:157
score = 0
if hwnd == prefer_hwnd:            score += 10**9   # 上次钉住的窗口
if is_wechat_main_title(title):    score += 10**6   # 标题像主窗
if foreground:                     score += 10**4   # 当前前台
if cls in ('QWindowIcon', mmui):   score += 10**3   # 微信主框架特征
score += min(area, 10**6)                            # 面积越大越像主窗
```

同时会过滤掉 `login` 窗口、没有 `Weixin.dll` 模块的进程、辅助小窗。

### 3.4 UIA 树：为什么"看得到窗口却点不到东西"

微信 4.x 的 UI 树默认**不物化**（accessibility 是懒加载的），所以 `uiautomation` 拿到的是一个空壳。解决办法是热写内部的 `QAccessible` 激活标志：

```python
# runtime/python/Lib/site-packages/wechatauto/accessibility.py
QACCESSIBLE_ACTIVE_RVA_BY_VERSION = {
    "4.1.11.22": 0x0A1E7DB8,
    "4.1.13.65": 0x0AE2B0C8,
    "4.1.15.13": 0x0B135C38,
    "4.1.15.53": 0x0B3959D8,
}
```

**微信一更新，这个表就失效**。4.2 之后我们不再依赖版本表，改成特征扫描：在 `Weixin.dll` 里扫候选 RVA，挨个试写，用"能不能找到 `mmui::ChatSessionList` 控件"作为验证，成功的那个写进本机缓存。

这一步失败的表现非常隐蔽：窗口能认出来，但点会话没反应、搜索框找不到、输入框定位错——**看起来像"机器人不听话"，其实是 UIA 树没建起来**。

## 四、人设：从"一段提示词"到"一套系统"

早期就是一大段 prompt，效果全靠运气。现在拆成几层：

| 层 | 内容 | 什么时候变 |
|---|---|---|
| 静态段 | 核心气质、说话方式、AI 味黑名单、四条硬边界 | 整个会话不变 |
| 动态段 | 此刻状态、活跃度、群文化、当前话题 | 每条消息重算 |
| 预设 | 7 套人设（标准 / 白璃 / 宅女鲸鲸 / 大肥鱼 / 有性子版 / 贴吧老油子 / 吵架大赛） | 用户切换 |

预设按**攻击力**从低到高排，文件里就写明了：

```json
{
  "id": "persona-baili",
  "order": 20,
  "name": "群友版：白璃（一张白纸）（低攻击力）",
  "customPrompt": "…"
}
```

`order` 决定启动器下拉里的顺序。这样做的原因是：群友之间会互相分享提示词，别人发来的全文太长（有的 2 万字），我们又不能无损塞进 6000 字的上限——那就干脆把"攻击力"作为第一排序维度，用户自己按需要挑。

还有一个细节：很多人设里写着"只发文字"。这时候用户说"发个语音"，模型会回"我没有麦克风"。所以每个预设都必须写清楚**"程序会把这段文字合成语音发出去，别说自己没麦克风"**——这行提示词比很多功能代码都重要。

## 五、语音：两个踩了两天的坑

语音分两路：

- **收**：微信语音消息 → 本地 pysilk 解码 → ASR 转文字 → 当普通消息处理
- **发**：她的回复 → TTS 合成 wav → 通过虚拟声卡播放 → 录音 → 作为语音条发送

第二条路上遇到了两个完全不是"代码逻辑"的问题：

### 坑一：.NET 的 HttpClient 默认走 HTTP/1.1，而这个接口在 HTTP/1.1 上连 TCP 都建不起来

现象是每次合成都在 20~30 秒后超时，日志写"语音合成超时"。用 curl 测同一个接口 41 秒能拿到音频，所以一开始以为是"接口慢"。

后来写了探针才发现：

```
HTTP/1.1 直连   → 20 秒 ConnectTimeout，连接都建立不了
HTTP/2   直连   → 12.9 秒，拿到 153 KB wav
```

**强制 `DefaultRequestVersion = Version20` 就好了。** 同一台机器、同一个 Key、同一个请求体，只是协议版本不同。

### 坑二：本机代理会吃掉这个请求

这台机器上设了 `HTTP_PROXY=http://127.0.0.1:7897`（Clash）。Node 内核启动时会清掉这些环境变量，但**启动器的 TTS worker 是 .NET 写的，它会读环境变量走代理** → 请求进了 Clash → 6 分钟没回来。

修法是在 HttpClient 上显式 `UseProxy = false`。国内接口，不需要代理。

两个坑修完之后，合成时间从"必然超时"变成 5~15 秒。

## 六、隐私与安全：几条不能破的线

- HTTP 服务**只绑 `127.0.0.1`**，没有登录层，所以文档里第一条就是"永远不要暴露到公网"
- 所有模型调用从本机直连服务商，不经过我们的服务器
- `data/`（记忆）、`config.json`（Key）在 `.gitignore` 里，且**日志自动脱敏**：`sk-xxx`、`wxid_xxx`、手机号会被打码；朋友圈正文、评论者信息不进内核日志
- 桥接与内核之间的接口带 token，朋友圈相关接口额外强制 loopback
- 不做的事：不 patch 微信、不注入、不修改微信文件

红线也很明确（写进人设里的四条硬边界）：不碰色情、不咒家人死、不搞地域/性别/疾病歧视、不威胁线下。

## 七、工程化：一个"随便玩玩"的项目长成了什么样

- **测试 1397 项**（Node `node:test` + 少量 Python 用例），CI 每次 push 都跑
- 分层检查脚本：`core` 不许 require `services`，`persona` 不许 require `pipeline`……防止架构腐化

- **安装包 181 MB**（含 .NET 10 桌面运行时、Python、Node、虚拟声卡驱动安装器）
- 许可证 4.0.x 起从 MIT 改成 **AGPL-3.0-only**（允许商用，但分发修改版要开源）

做这个东西最深的体会是：**模型能力早就够了，难的是"怎么让它活在一个为人类设计的软件里"**。
