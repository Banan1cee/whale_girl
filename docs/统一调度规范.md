# 统一信息调度规范

> 状态：设计规范，分阶段落地。第 2、2.1 节描述的是当前代码已实现的行为；第 4 节执行类别、第 5 节多数硬取消/隔离要求仍是目标约束，落地前不得据此假定运行时代码已具备对应能力。
> 目的：让内核功能实现可替换、跨组件调用可治理，并避免排队和长任务阻塞聊天关键路径。
> 能力命名、schema 与兼容规则见 [能力契约规范](能力契约规范.md)。

## 1. 目标与非目标

统一调度层解决两类问题：

1. **稳定边界**：调用方依赖稳定能力契约，不依赖服务类、文件路径、内部函数名或队列实现。功能可以拆分、换存储、换执行器，只要契约语义不变，插件无需适配。
2. **执行治理**：为可调度工作提供有界排队、并发隔离、截止时间、取消传播、背压、幂等和状态观测。

它不是把所有函数调用改造成异步消息的通用总线，不取代 HTTP/桥接传输协议，不承诺所有任务都可取消，也不把“已接收/已排队”伪装为“已完成/已送达”。

## 2. 三层边界

```text
传输适配层（HTTP / 桥接 / 插件 host.call / 定时任务）
                         ↓
稳定能力契约层（能力 ID + schema + 权限 + 可观察语义）
                         ↓
执行治理层（同步直调 / 有界队列 / 隔离执行器 / 取消与截止时间）
                         ↓
功能适配器与可替换实现（services/features/* → 业务服务）
```

- **传输适配层**负责身份、鉴权、协议解析、状态码和传输生命周期。不得复制业务规则。
- **能力契约层**负责唯一登记、输入输出校验、权限与调用来源判定。插件只见公开能力，宿主内部能力不因此自动开放给插件。
- **执行治理层**按能力策略选择执行方式。调度队列、线程/worker、优先级、重试与监控属于宿主内部实现，不是插件 API。
- **功能实现层**负责业务。实现可重构，只要保持能力的外部语义和已登记 schema。

当前 `runtime.capabilities.invokeHost` 是宿主能力统一入口；`src/services/features/index.js` 是 handler 唯一装配点。当前实现为**每项宿主能力独立的有界准入**：默认最多同时执行 32 个、另有 128 个 FIFO 等待位置，慢能力不占用其他能力的名额。构造参数 `maxHostConcurrent`（整数 1–256）和 `maxHostPending`（整数 0–4096）设置每项能力的上限；`maxHostWaitMs` 默认 30000（整数 1–2147483647 毫秒）限制排队时间，与调用方 deadline 取先到者。即使内部调用没有 deadline，排队也有限；准入后该排队预算不再约束 handler 执行时长。这些不是插件公开参数，也不代表跨能力的全局资源预算；同一能力内插件与宿主共享容量。

等待中的调用可因 signal 取消或 deadline 到期离队，满载报宿主诊断码 `host_capability_queue_limit`；进入 handler 前再次校验插件授权及声明。同能力嵌套调用报 `host_capability_reentrant`；不同能力嵌套在目标池有空位时可执行，目标池已满则快速拒绝，避免持有外层名额等待下游产生自等。该保护只覆盖同一 dispatcher 异步调用上下文，不是跨进程依赖环检测。

运行中的 handler 不被强制中断，deadline/signal 仍沿用原有执行前后检查：若 handler 不返回，调用方也仍在等待，名额持续占用；handler 返回后可能报超时/取消，**这不证明副作用未发生**，分发器不自动重试。仍未实现运行时硬截止、CPU/原生工作隔离、资源域共享池/全局额度、优先级、自动重试、统一持久化任务、池级指标或统一关闭语义。后文对此类机制的要求仍是目标约束，不能当作已实现事实。

本阶段新增的宿主诊断码为：`invalid_dispatcher_limits`（构造参数不是允许范围内整数）、`host_capability_queue_limit`（等待队列满，或嵌套调用的目标池已满）、`host_capability_reentrant`（活动祖先中存在同能力调用）。嵌套满池拒绝是保守策略，即使占用者与祖先无关也不等待，以避免两个根调用分别持有上游名额并交叉等待；它不是精确依赖图判环。插件 Worker 对这些执行诊断仍按现有宿主失败映射处理，不新增插件可见返回结构。

### 2.1 嵌套宿主调用的预算与取消继承（第二阶段现状）

第二阶段的实现范围只有一件事：**同一 dispatcher、仍在活动调用上下文内的嵌套 `invokeHost` 会继承上游预算与取消**。它不改注册表、不改插件公开 schema/授权、不改上节准入参数，也不改变失败码集合。

继承规则（以 `src/services/unifiedCapabilityDispatcher.js` 的 `inheritHostContext()` 为准）：

- **deadline 取父与子的较小值，只收缩不扩张**。父有 deadline 而子没有 → 用父的；父与子都有 → 取较小；只有子有 → 用子的。子调用永远拿不到比父更长的新预算。
- **signal 按来源合并**。父 frame 记录的是它自己订阅的**信号来源集合**（`sources`），不是某一个中间派生的 signal。子调用把「父的来源集合」与「本次调用方传入的 signal」去重后合并；多于一个来源时新建一个派生 `AbortController`，对每个来源**各自** `addEventListener('abort', …, { once: true })` 并在 `invokeHost` 的 `finally` 中全部移除；只有一个来源时直接共用，不派生。因此监听开销只看**去重后的来源数量**：`sources` 去重后为 1 时直接共用该 signal、不派生也不新增监听（不管子调用自己有没有再传一个已被父覆盖的来源）；去重后 ≥2 时必须派生，并对每个来源各挂一个监听，同一父来源下有 N 个这样的并发派生调用就对应 N 个监听，直到各自 settle 才移除。注意父的 `sources` 本身可能已经 ≥2，此时子调用即使不带自己的 signal，也会因去重后来源仍 ≥2 而派生并新增监听。这是继承的固有代价，不引入全局合流池。
- **中间层 settle 不切断后代的取消链**。因为 frame 存的是来源全集，子/孙调用会重新订阅同一组源：即使中间层早已返回并释放了自己的监听，只要更上层的来源还没结算，孙调用仍能收到取消。
- **已结束的调用不再作为祖先**。取祖先时只保留 `frame.active` 的条目，所以从某个已 settle 的调用上下文中延后发起的调用，**只有在没有其他 `active` 祖先时**才按新的根调用处理。若更上层仍在执行（例如中间层 B 已返回、外层 A 还没结束），延后发起的调用仍然继承仍活动的祖先（A）的 signal 和 deadline；只有整条链都结束，才不再继承。

生效范围与明确不承诺的部分：

- 继承只在**同一个 dispatcher 实例、同一个 AsyncLocalStorage 活动上下文**内生效；不是跨进程、跨 worker 或跨 dispatcher 的依赖环检测，也不是跨能力的全局预算账户。
- **根请求必须带上下文源，嵌套可省略**。继承靠的是活动上下文，不是每次调用都重复传参：只要调用发生在**同一 dispatcher 的 ACTIVE `invokeHost` handler 内部**，即使像 `features/hostCall.js` 的 `hostCall(runtime, 能力, 输入)` 那样完全不传 `signal`/`deadline`，也会自动继承祖先的预算与取消；显式传入只是追加一个来源。反过来，HTTP 路由入口、普通 Bot 主流程这类调用既不在活动宿主上下文里、本身又没带 signal/deadline，就不会凭空获得预算——预算必须由最外层请求提供，内层才谈得上继承。注意 `invoke()`（provider 编排：聊天接管、生成、回复改写、检索替补等）与 `invokeHost()` 是两条路径，`invoke()` 不写入宿主继承上下文；因此在 provider builtin 或 Bot 主流程里发起的 `invokeHost` 不算嵌套，除非它本身位于某个活动 `invokeHost` handler 之内。该轮次把 signal 透传给宿主能力属于下一步接线范围，不得描述成已全局生效。
- 继承没有引入运行时硬截止：不新增打断 handler 的 timer；继承来的 deadline 只在准入前、执行前、执行后三处检查，以及经 handler 传入下游 I/O。
- 所有祖先都已 settle 之后才从该上下文发起的 detached 子调用**不受这些已结束祖先的影响**（按新根处理）。但若链上还有其他仍 `active` 的祖先，这些延后调用仍会继承那个祖先；也就是说「settle 后不继承」以**没有其他活动祖先**为前提。注意**自带 signal/deadline 并不能切断继承**：只要调用发生在活动的宿主上下文内，自己传的 deadline 仍与祖先取较小值、signal 仍与祖先来源合并，无法借此脱离。需要真正独立于原有调度的任务，应在**不存在活动宿主上下文的新根入口**里发起（例如独立的入口/调度路径），或使用将来专门的任务能力；当前不承诺「显式传入 signal 即可不被继承」。
- 忽略 signal 的 handler 在超时/取消后仍占用其名额直到真正返回，本阶段不变（见第 5 节）。

真实只读试点是 `search.query@1`：它是当前注册表里唯一 `sideEffect: network-read` 的宿主能力，也是插件与宿主共用的检索入口。handler 先按输入把预算 clamp 到 500–30000ms，再用 `deadline - now` 压一层并取较小值。**剩余预算不足 500ms 时不会被抬回 500ms**：过期即报 `capability_timeout` 且不启动下层检索，已取消则报 `capability_aborted` 且不触碰下层。验收见 `tests/feature-capabilities-search-budget.test.js` 与 `tests/unified-host-dispatch.test.js`。

## 3. 哪些调用经过调度

### 3.1 应通过稳定能力边界

- 外部入口触发的用例：HTTP、桥接、插件、定时任务。
- 跨功能域的读写或命令：例如提醒创建、记忆读写、消息发送、朋友圈操作。
- 可能等待网络、模型、文件系统、微信桥接或其他有限资源的工作。
- 需要独立权限、超时、限流、取消、幂等或运行状态的任务。

入口只把请求翻译为契约输入并调用分发器；不得绕过分发器直接调用业务 handler，也不得另建一套插件专用 SDK 路由。

### 3.2 保留同步直接调用

以下调用不强制经过队列：

- 无 I/O、短小、确定的纯函数和结构转换。
- 同一用例内必须原子完成的局部步骤。
- 需要同步返回、且已证明短时有界的内部读取/装配，例如提示词构建期间的同步上下文拼装。
- 仅用于依赖注入、回调装配或同一模块内部私有协作的调用。

若直接调用开始执行慢 I/O、等待外部进程或显著增加延迟，应把该工作提取为能力/任务，再由同步边界明确 await 或使用已有快照；不得为了统一形式把纯逻辑异步化。

### 3.3 禁止形成隐式事件网

不得建立任意字符串事件、隐式订阅者、跨域可变共享 payload 或依赖订阅顺序的业务总线。异步命令必须有稳定能力 ID、schema、所有者、可追踪任务 ID 和明确定义的终态。观察事件只能用于无业务副作用的观测，失败不得改变命令结果。

## 4. 执行类别与资源隔离

建议为能力声明一个执行类别，类别决定宿主的队列和资源策略；它是内部调度元数据，除非明确写入插件公开契约，否则插件不可依赖具体数值。

| 类别 | 示例 | 调度要求 |
| --- | --- | --- |
| `inline` | 纯逻辑、内存内快速校验 | 不入队；必须短时有界，不得做阻塞 I/O |
| `request` | 本机读取/写入、短网络查询 | 有并发上限及总 deadline；队列容量有限；请求结束时传播取消 |
| `chat-serial` | 同一会话必须顺序的聊天处理 | 按会话键串行、跨会话并行；每会话及全局队列都有限；不得被无关后台任务占满 |
| `background` | 日记、汇总、可延迟计算 | 独立低优先级池；满载时拒绝或合并，不挤占聊天池；持久化语义单独声明 |
| `external-effect` | 微信发送、朋友圈发布等外部动作 | 有界提交/发送池；使用幂等标识及显式领取/回执；状态未知时不得自动重发 |
| `isolated` | 可能阻塞主线程或不可合作取消的 CPU/原生/第三方工作 | 移至独立 Worker/子进程；通过 IPC 限长；超时可终止隔离执行单元，不阻塞 Node 主事件循环 |

队列按资源域分池，不能让任一低优先级慢服务占满所有调用。优先级仅影响**尚未开始**的队列任务，不可抢占已运行任务；同优先级保持可预测的 FIFO，`chat-serial` 额外保证同 key 顺序。防饥饿时必须给高优先级留出可配置预算或采用老化策略，不能承诺严格优先且无饥饿两者兼得。

## 5. 有界队列、deadline 与取消

每个可排队类别至少定义：最大总等待数、最大每 key 等待数（适用时）、并发上限、最大排队时间、执行 deadline、满载行为和关闭行为。参数应有安全默认与上限；不能由不可信插件任意调高。

- **拒绝优于无限堆积**：容量耗尽时快速返回稳定的 `busy`/`queue_full` 类结果，不在内存中无限保存任务。
- **总预算而非重置超时**：deadline 从首次接收时计算，排队、执行和内部下游调用共用剩余预算，层层调用不得重新获得一份完整超时。当前只在同一 dispatcher 的活动嵌套 `invokeHost` 之间自动继承（见 2.1）；跨进程、跨 provider `invoke()`、LLM 调用以及其他同步直连路径尚未统一接线，不能按本节假定已普遍生效。
- **排队取消**：未开始的任务收到取消后立即移出队列并释放容量，不调用 handler。
- **运行中取消**：通过 `AbortSignal` 传递至 HTTP/文件/模型等合作式 I/O；handler 必须在安全点检查 signal。副作用已提交后不得以“取消成功”暗示副作用已撤销。
- **不支持取消**：设置 deadline 只结束调用方等待，不表示底层工作停止。必须将工作放在独立可终止的隔离单元，或标记 `timed_out_but_running` 并计入资源上限；禁止用未受控的 `Promise.race` 假装释放资源。
- **超时语义**：超时期间若外部副作用结果不确定，返回可识别的未知/处理中状态和任务 ID；不得把未知转换成普通失败后自动重试。
- **关机**：停止接收新任务；未开始任务按类别拒绝或明确持久化；已开始任务在有界宽限期内完成或取消。不能默默丢弃有持久化承诺的工作。

## 6. 返回、错误与副作用

同步能力返回经过 schema 校验的结果。后台或外部动作可返回 `accepted/queued` 与任务 ID；后续状态通过明确的查询/回执能力取得。所有结果都必须区分“输入被接受”“handler 完成”“外部系统确认”，例如桥接网关已提交不等于微信用户已收到。

失败分类至少区分：未登记/未开放、输入无效、未授权、队列满、deadline 超时、调用取消、执行失败、外部结果未知、幂等冲突。插件可见错误由公开契约映射；内部错误码与实现堆栈不得自动成为插件分支依据。记录错误不得泄露聊天正文、记忆正文、密钥或完整敏感 payload。

| 副作用等级 | 失败处理原则 |
| --- | --- |
| 无副作用 | 可安全重试（仍受总 deadline 和次数上限约束） |
| 只读网络 | 可按能力策略有限重试；遵守取消、超时和服务商限制 |
| 本地写入 | 需事务/原子写或幂等键；不可盲目重复提交 |
| 计费调用 | 明确费用与重试次数；超时后不能假设供应商未计费 |
| 外部消息/动作 | 需要幂等键、任务状态或桥接回执；未知状态不自动重发 |

幂等键应由调用边界生成并跨重试保留，作用域至少含能力 ID、调用者/任务和业务目标；键不可代替授权。去重保留期须覆盖最大重试与回执窗口。现有能力各自的状态语义优先保留，不能通过统一包装改变已发布行为。

## 7. 可观测性与数据边界

每次调用至少可关联：trace/correlation ID、能力 ID 与版本、调用来源类别（不含秘密）、执行类别、排队时长、运行时长、剩余 deadline、终态/错误分类、重试次数、幂等命中及副作用阶段。聚合指标观察队列深度、拒绝率、超时率、池占用与长尾延迟。

默认只记录结构和计数，不记录聊天正文、记忆正文、API Key、微信 ID、插件私密设置或原始 payload。高基数会话键只用于短期内部关联，不作为指标标签；日志里的标识须遵守项目隐私规范。

## 8. 能力重构与兼容

- 替换实现、拆分服务或迁移存储，只要能力的输入、输出、授权、副作用和完成语义不变，不改插件契约。
- 改变字段语义、权限范围、发送确认含义、可重试性或成功时机，属于契约改变，不能只换 handler；新增兼容版本并保留旧版本迁移期。
- 新能力默认只供宿主内部；开放插件须单独评估数据最小化、授权提示、执行预算与等级白名单。
- 废弃能力先停止新增依赖、提供替代能力、保留兼容窗口与明确诊断，再按版本策略移除。不得因内部重构静默删除或复用旧 ID。

## 9. 渐进落地

1. **盘点**：给现有能力标出调用方、I/O、同步依赖、副作用和当前超时/队列；不改行为。
2. **先定声明**：确定执行类别、deadline 口径、满载错误与终态语义；登记缺口，但不要一次性迁移所有功能。
3. **只读试点**：挑一个网络读取能力，引入有界并发、共享 deadline、取消传递和队列满测试；确认不影响聊天池。（已选 `search.query@1` 落地：预算 clamp + 剩余预算只收缩、活动嵌套继承，见 2.1。）
4. **副作用试点**：选消息发送队列，明确任务 ID、幂等、queued/claimed/submitted/acknowledged 语义和未知结果处理；保持既有桥接契约。
5. **逐域迁移**：一次迁移一个能力及调用方，旧路径与新路径不能并行产生副作用；每批可回退且覆盖真实入口。
6. **评估后再迁移**：聊天管线、提示词装配和必须同步读取保持现状，只有证明收益且能保持顺序/时延语义后才提出专案。

## 10. 验收场景

- 慢网络调用达到并发上限后，队列深度有界；容量满时调用快速失败，聊天回复仍可继续。
- 取消等待中的任务后，handler 从未执行且队列计数释放；取消合作式运行任务后，下游请求收到 signal。
- 忽略 signal 的测试 handler 超时后仍占用其隔离容量，不会被计作已释放；隔离执行单元可终止或明确报告仍运行。
- 同一会话任务严格顺序，不同会话可按并发预算运行；后台长任务不能阻塞聊天池。
- 发送任务超时且回执未知时不自动重复发送；同幂等键重放不会重复产生副作用。
- 更换能力 handler 但保留 schema 与语义时，既有插件包无需修改；未获授权插件仍不能调用。
- 日志/指标不包含正文、密钥或高基数隐私字段；队列满、超时和外部未知状态能从错误分类中区分。

第二阶段已落地并可从公共边界验收的场景（见 `tests/unified-host-dispatch.test.js`、`tests/feature-capabilities-search-budget.test.js`）：

- 活动 `invokeHost` handler 内嵌套调用时，deadline 取父子较小值：父更短用父、子更短用子、子不带用父，任何方向都不会获得更长预算。
- 父 signal 取消会中止带自己 signal 的子调用；取消子调用自己的 signal 不会反向取消父；`invokeHost` settle 后父 signal 与子 signal 上的继承监听都被移除。
- 三层嵌套中，中间层先 settle 也不切断孙调用的取消链；只有整条链都 settle 之后才发起的延后回调按新根调用处理，不继承旧 signal/deadline；若此时仍有更上层的 `active` 祖先，延后回调仍继承该祖先。
- `search.query@1` 在剩余预算不足 500ms 时不会抬高到 500ms；已过期报 `capability_timeout`、已取消报 `capability_aborted`，两者都不启动下层检索。
- 继承不改变非硬取消语义：handler 忽略 signal 时照旧占着名额直到真正返回，超时/取消只在检查点报错，不重试、不宣告副作用已撤销。
