# 鲸鲸插件市场规范

当前只有一种可执行插件协议：**whale-plugin/1**（见 [插件协议](插件协议.md)）。
人设包（纯数据）继续支持。

## 1. 哪些东西能装

| 类型 | 说明 | 现状 |
| --- | --- | --- |
| 统一协议插件 | ZIP 根目录含 `plugin.json`，以及 1–3 级的 `plugin.wasm` 或 4 级的 `plugin.js` | 支持本地安装与试装 |
| 人设包 | 纯数据 `plugin.json` + `persona.json`，不执行代码 | 支持本地安装与分享 |

远端 `Banan1cee/whale-girl-plugins` 目前只发布 `index-personas.json`；新协议目录 `index-v5.json` 的接入步骤见本文「新协议目录接入」一节。
启动器只读取真实存在的人设目录，不会把旧目录当成新协议来源。
新协议的公开投稿要等市场仓库同步目录生成、校验与 CI 之后才开放。

## 2. 客户端版本与代次

- `minAppVersion` / `maxAppVersion` 决定能装到哪个鲸鲸版本。
- `appEpoch`（1 = 旧 4.x 体系，2 = 正式版体系）解决 4.x 与 1.x 不能直接比较数字的问题。
- 需要同时兼容两代时用 `appCompatibility`：

```json
{
  "minAppVersion": "4.3.0",
  "appCompatibility": [
    { "appEpoch": 1, "minAppVersion": "4.3.0" }
  ]
}
```

数组 1–2 项，同代不能重复；每项可选 `maxAppVersion`，且不得小于该项下限。
顶层 `minAppVersion` 仍要保留真实范围。

## 3. 授权与数据

- 安装只解包校验，不执行、不授权；保存设置也不会生成授权。
- 1–3 级使用受限 Wasm，3 级回复扩展须确认聊天访问。4 级才须确认「完整系统权限」。Node 插件**不是沙箱**：它可以读写文件、联网、启动进程；
  `calls` 只限制宿主代为执行的能力，不限制代码本身。
- 每次启用签发的授权绑定：插件 ID、安装包 SHA-256、清单与入口原始字节摘要、授权代次、
  批准的 provider 列表、已启用且用户同意的 call 列表、设置快照。
- 修改设置、更新版本、停用都会重签或撤销授权；旧代次的迟到结果被丢弃。
- 宿主暂未开放的调用（`message.submit@1`）可以声明，但不会获批，也不会执行。
- 宿主管理的调用不提供模型密钥或微信凭据，但 4 级代码仍有系统权限。需要模型或检索时，通过获授权的 `model.complete@1` / `search.query@1` 代办。

## 4. 能力与作用域

能力、模式、作用域和输入输出 schema 由宿主注册表统一维护
（`src/services/pluginProtocolRegistry.json`），启动器、运行时和作者 CLI 读的是同一份定义。
同一能力同一作用域只允许一个 `replace` 提供者；冲突在调用任何插件之前拒绝。

## 5. 操作入口

- 插件只能在「插件市场 → 已安装」里管理：启用、停用、卸载、设置、手动运行。
- 插件不得往左侧工作台、状态页、系统设置页或托盘自行加入口。
- 手动运行只有 `tool.run@1`，输入按插件 `settingsSchema` 之外的 JSON 原样传入。
- 插件总开关 `features.plugins` 默认关闭；关闭会停止受管理的 Worker 并取消未执行调用。

## 6. 免责声明与风险

- 上架、扫描、签名都不构成无毒保证或官方安全认证。
- 作者和代交者须如实说明来源、功能、权限、兼容范围和已知风险。
- 完整说明见随包「插件免责声明.md」。

## 7. 投稿（尚未开放新协议）

新协议开放投稿前，市场仓库需要先完成：目录生成（`index-v5.json`）、清单与能力校验、
ZIP 摘要核对、在固定宿主环境里的模拟执行与撤销测试。在那之前：

- 可以本地打包、安装、试装，但不能宣称「已上架」或「已通过市场校验」；
- 统一协议投稿 PR 暂不接受，避免目录里出现客户端无法验证的条目。

## 新协议目录接入（whale-girl-plugins）

### 1. 目录

```text
index-v5.json      # 新协议插件目录（新增）
index-personas.json # 人设包，保持不变
packages/<id>-<version>.zip
plugins/<id>/plugin.json
```

旧目录 `index.json` / `index-v2.json` / `index-v3.json` / `index-v4.json` 冻结，不再新增条目；新协议只进 `index-v5.json`。

### 2. 目录条目

`build-index.js` 从 `plugins/<id>/plugin.json` 生成，字段：

```json
{
  "Id": "word-count",
  "Name": "字数统计",
  "Author": "作者",
  "Version": "1.0.0",
  "Level": 2,
  "MinAppVersion": "4.3.0",
  "MaxAppVersion": null,
  "appEpoch": 1,
  "appCompatibility": [{ "appEpoch": 1, "minAppVersion": "4.3.0" }],
  "Description": "统计输入文本的字数",
  "Provides": { "tool.run@1": { "mode": "tool", "scope": "manual" } },
  "Calls": [],
  "DataAccess": [],
  "ExecutionTimeoutMs": 30000,
  "Download": "https://example.com/word-count-1.0.0.zip",
  "Sha256": "…",
  "DiscussionIssue": 0
}
```

- `Level` 取 1–4；`Provides`、`Calls`、`DataAccess` 必须与包内 `plugin.json` 完全一致。
- 上面的 `example.com` 是占位地址，不代表存在已发布安装包。市场接入后，实际下载地址固定为官方市场仓库的 `main/packages/<id>-<version>.zip`；`Sha256` 由 CI 计算，投稿人不填。
- 目录不写 `Api`、`Hooks`、`Permissions`、`HostAction`；这些属于旧接口。

### 3. 校验器

`validate.py` 加 `index-v5.json` 分支，逐条校验：

1. ZIP 根目录正好两项：`plugin.json` 与入口文件。
2. 入口 = `plugin.wasm`（Level 1–3）或 `plugin.js`（Level 4），与 `Level` 对应。
3. 清单必填字段齐全、无未知字段；`Format` 为 `whale-plugin/1`。
4. `Provides` 的能力在等级允许列表内，`mode`/`scope` 合法；`task.tick@1` 校验 `intervalSeconds`。
5. `Calls` 在等级允许列表内且不重复；`DataAccess` 只允许 Level 3、且必须同时声明 `chat.reply@1`。
6. Level 1–3：`plugin.wasm` 以 `\0asm` 开头，≤512 KiB，导入只允许 `whale_plugin.input_size/input_byte/output_byte`。
   Level 4：`plugin.js` 为 UTF-8、≤8 MiB。
7. `appCompatibility` 1–2 项、同代不重复；`Version`/`MinAppVersion` 为数字版本。
8. 目录条目与包内清单逐字段一致；`Sha256` 与 ZIP 实际摘要一致；ZIP 总大小 ≤16 MiB。

第 4–5 步的允许列表从市场仓库内的 `protocol.json` 读取，该文件由宿主 `pluginProtocolRegistry.json` 复制而来，
两边必须同版本；升级协议时先同步它。

`test_validate.py` 至少覆盖：越级 `Provides`、1/2 级声明 `DataAccess`、错误入口、非 Wasm 字节、
`Calls` 未开放、目录与包不一致、摘要不符。

### 4. CI

- 现有 `validate.yml` 增加 v5 校验，并在 `main` 设为必需检查。
- 拒绝未知字段与未知等级，不要静默跳过。
- 目录由 CI 生成；PR 只允许改 `plugins/<id>/` 与 `packages/<id>-<version>.zip`。
- 旧目录的签名与检测流程保持不变；v5 先做静态校验与摘要核对，动态模拟执行可后置。

### 5. 客户端读取

宿主 `launcher/PluginCatalog.cs` 目前只拉 `index-personas.json`。市场发布 `index-v5.json` 后：

- 增加该目录的下载与解析，映射到 `PluginInfo` 的 `Level`、`Provides`、`Calls`、`DataAccess`。
- 安装仍走现有 `ReadPackage` 校验，并比对目录条目与包内清单。
- 目录尚未存在时保持现状（只显示人设），不要显示空市场。

### 6. 投稿流程

作者交三样：`plugins/<id>/plugin.json`、`packages/<id>-<version>.zip`、可审核源码说明。
PR 目标固定 `Banan1cee/whale-girl-plugins:main`；同一 ID 升版本、作者不变。
CI 通过后合并，客户端刷新即可看到。

### 7. 完成标准

- `index-v5.json` 能由 CI 生成并通过校验。
- 1–4 级各有一个示例包通过安装、授权、运行、停用。
- 宿主能读取目录并安装；旧目录不再产生新条目。


## 目录与插件包签名（当前隐藏）

### 当前状态：已隐藏

当前版本暂时把整套验签藏起来了：启动器不再下载 `index*.json.sig`，条目里的 `Signature` 只解析不校验，
插件卡片也不再显示“已签名 / 未签名目录”。市场只按下载域名白名单、SHA-256 和包内清单一致安装。

代码、公钥、签名工具（`scripts/plugin-market-sign.js`）和回归都完整保留，后续要恢复时：

1. 把 `launcher/PluginMarket.cs` 的 `MarketSignatureEnabled` 改成 `true`；
2. 重新发布 `WhaleLauncher.exe`；
3. 按下面的流程给市场和插件包补签名。

恢复后规则如下（隐藏期间不生效）：**有 `.sig` / `Signature` 就必须验过，没有就按未签名加载**；
仍然校验 SHA-256、下载域名白名单和包内清单一致性。市场仓库还没配私钥时，未签名目录属于正常状态，
不会把整个市场挡在门外。

### 信任根

- 公钥在 `launcher/PluginTrust.cs`，当前指纹（SHA-256）：
  `135bd43efa206a50668291659154e74cb85779ca33cb13da61176b15736f7418`
  替换公钥后请同步更新这里的指纹。
- 私钥只在维护者离线环境，禁止提交到仓库。`.gitignore` 已忽略
  `plugin-market-private-key.pem` 和 `*.private.pem`。
- 公钥轮换时，把新公钥追加到 `DefaultPublicKeys`，用逗号或换行分隔；旧公钥至少保留一个发布周期，
  让用户能平滑更新。

### 目录签名

每个目录文件旁边放一个同名 `.sig` 文件：

```
index.json
index.json.sig
index-v2.json
index-v2.json.sig
index-v5.json
index-v5.json.sig
```

`.sig` 是目录原始字节的 ECDSA/SHA-256 签名，Base64 编码，可以带一个结尾换行。
恢复验签后，启动器先下载目录字节，再下载 `.sig`，验签通过才解析。`index.json` 验签失败会直接拒绝市场；
`index-v2.json` / `index-v5.json` 等可选目录缺签名或验签失败时跳过，不影响主目录。

### 插件包签名

目录条目的 `Signature` 字段是 ZIP 原始字节的 Base64 签名：

```json
{
  "Id": "line-counter",
  "Version": "1.0.0",
  "Download": "https://github.com/.../line-counter-1.0.0.zip",
  "Sha256": "……",
  "Signature": "MEUCIQ……"
}
```

恢复验签后，启动器安装时会同时检查：

1. `Signature` 对下载字节验签；
2. `Sha256` 与下载字节一致；
3. 包内 `plugin.json` 与目录条目除下载地址、哈希、讨论编号和签名外完全一致。

本地 ZIP 没有市场签名，仍可安装，但确认框会明确标注“未经市场审核或签名”。

### 维护者操作

准备私钥（只生成一次，离线保存）：

```powershell
node -e "const {generateKeyPairSync}=require('crypto');const {publicKey,privateKey}=generateKeyPairSync('ec',{namedCurve:'P-256'});require('fs').writeFileSync('plugin-market-public-key.txt',publicKey.export({type:'spki',format:'der'}).toString('base64'));require('fs').writeFileSync('plugin-market-private-key.pem',privateKey.export({type:'pkcs8',format:'pem'}))"
```

把公钥内容替换到 `launcher/PluginTrust.cs` 的 `DefaultPublicKeys`，私钥留在离线机器。
替换后同步更新本文「目录与插件包签名」一节的指纹，以及 `tests/plugin-market/Program.cs` 里用旧私钥生成的
`node-signed payload` 测试签名，否则回归会明确失败。

给插件包签名：

```powershell
node scripts/plugin-market-sign.js package dist/line-counter-1.0.0.zip --key plugin-market-private-key.pem
```

把输出的 Base64 填进目录条目的 `Signature`。然后签目录：

```powershell
node scripts/plugin-market-sign.js catalog index.json --key plugin-market-private-key.pem
node scripts/plugin-market-sign.js catalog index-v2.json --key plugin-market-private-key.pem
node scripts/plugin-market-sign.js catalog index-v5.json --key plugin-market-private-key.pem
```

最后用公钥复核：

```powershell
node scripts/plugin-market-sign.js verify index.json --signature-file index.json.sig --public-key plugin-market-public-key.txt
```

### 发布顺序

1. 有私钥时，先用同一把私钥给目录和要上架的 ZIP 签名；
2. 再合并市场目录；
3. 把开关改为 `true` 并重发 EXE 后，客户端才会验签；隐藏期间第 1、2 步可以先做，客户端只当普通字段解析。

签名是加强项而不是前置条件：市场仓库还没配私钥时，未签名目录照常可用，主依据仍是
“市场仓库的固定版本 + SHA-256 + 下载域名白名单 + 包内清单一致”。等私钥就位再逐步补齐签名，
不需要为了等签名把市场整个关掉。
